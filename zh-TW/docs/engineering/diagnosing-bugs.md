## 它做什麼

`diagnosing-bugs` 對一個棘手的 bug 或效能退化執行六個階段的診斷：建立重現案例、最小化它、為假設排序、加入觀測、連同回歸測試一起修正、清理。

在一個**緊密（tight）**的回饋迴圈存在之前，它不會讓 agent 形成理論：一個已經執行過一次的具名指令，會在*這個* bug 上亮紅燈，並在修好時轉綠。拿到一份 bug 回報時，coding agent 預設會讀程式碼然後猜。這個 skill 阻擋了這件事。如果沒有能亮紅燈的指令，就沒有階段 2。這一道關卡就是這個 skill 存在的目的。一旦迴圈存在，之後的一切（二分搜尋、假設驗證、觀測）都是機械性的。

## 何時使用

輸入 `/diagnosing-bugs`，或者當任務適合時，agent 會自己使用它。它是模型觸發的，會在「diagnose（診斷）」或「debug this（幫我除錯）」，或回報某個東西壞了、拋出例外、失敗或變慢時觸發。

把它用在棘手的情況上：第一眼解決不了的 bug、時好時壞的不穩定問題、在兩個已知正常的狀態之間引入的退化。它是刻意又慢又徹底的，所以對於一個你希望一則訊息就得到答案的問題，它是錯的工具。

| 你的情況 | 去哪裡 |
| --- | --- |
| 一個你能以症狀描述的具體缺陷 | 這個 skill |
| 一個很慢的 endpoint，或一個已知前後狀態的時間退化 | 這個 skill。它有一個效能分支（先量測基準，再做二分搜尋） |
| 「這個程式碼庫的瓶頸在哪裡？」，沒有具體的症狀 | 不是這個 skill。它診斷一個已知的失敗，它不做稽核 |
| 一份來自別人、還沒確認或整理過的原始 bug 回報 | 先用 [triage](https://aihero.dev/skills-triage) |
| 用完即丟的程式碼來回答設計問題，而不是追查缺陷 | [prototype](https://aihero.dev/skills-prototype) |
| 以測試先行的方式建立一個規劃好的行為 | [tdd](https://aihero.dev/skills-tdd) |
| 修好之後，問問什麼本可以預防這個 bug | [retro](https://aihero.dev/skills-retro)，在同一個 session 中執行 |
| 沒有好的接縫可以把 bug 鎖住 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture)，由你自己啟動 |

## 緊密的迴圈就是這個 skill

階段 1 得到最多的心力，因為它是唯一困難的階段。skill 列出了建立迴圈的方法，大致依偏好順序排列：

1. 在任何能觸及 bug 的接縫上寫一個失敗的測試。
2. 對執行中的 dev server 執行 curl 或 HTTP 腳本。
3. 以固定的輸入做 CLI 呼叫，並與已知正確的快照做 diff。
4. 一個無頭瀏覽器腳本，對 DOM、主控台或網路做斷言。
5. 重播擷取的資料：一個存下來的請求、payload 或事件日誌，單獨透過程式路徑執行。
6. 一個用完即丟的測試架：系統的最小子集，一次函式呼叫。
7. 一個性質測試或模糊測試迴圈，用於「有時候輸出錯誤」。
8. 一個可以交給 `git bisect run` 的二分搜尋測試架。
9. 一個差異比對迴圈：同樣的輸入，舊版對新版。
10. 一個[人在迴圈中（human-in-the-loop）](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop)的 bash 腳本，最後手段。skill 為此附帶了 `scripts/hitl-loop.template.sh`：agent 執行腳本，你在終端機中依照提示操作，而你的回答會以可解析的輸出回傳。

*一個*迴圈不是目標。**緊密**才是：快速（幾秒鐘）、具確定性（每次執行的判定都一樣）、銳利（斷言你確切的症狀，而不是「沒有當掉」），而且 agent 不需要你就能執行。一個 30 秒、時好時壞的迴圈，只比沒有好一點點。對於一個只是偶爾出現的 bug，目標不是乾淨的重現，而是**更高的重現率**：反覆觸發、平行化、加壓、注入 sleep，直到不穩定的比率高到足以拿來除錯。

當 agent 建立不了迴圈時，skill 會告訴它停下來並直說、列出它嘗試過的方法，並向你要求[環境](https://www.aihero.dev/ai-coding-dictionary/environment)存取權、一份擷取的資料，或加入暫時性觀測的許可。它絕不能無論如何都繼續去形成假設。

## 階段之間的關卡

各個階段是關卡，而不是檢查清單。在某個特定條件成立之前，agent 不能進入一個階段。

| 關卡 | 必須成立的條件 |
| --- | --- |
| 進入階段 2 | 一個已經執行過、並連同輸出一起貼出的具名指令，能在這個 bug 上亮紅燈 |
| 進入階段 3 | 重現案例已經重現*而且*最小化：剩下的每個元素都是重現 bug 所必需的 |
| 進入階段 4 | 存在 3 到 5 個排序好、可證偽的假設，每一個都說明它的預測，並在任何一個被測試之前先給你看 |
| 進入階段 5 | 探針對應到一個具體的預測，一次只改一個變數，每一行除錯 log 都有一個像 `[DEBUG-a4f2]` 的標籤，這樣一次 grep 就能找到全部來清理 |
| 完成 | 原始的重現案例不再重現、觀測已移除，而且 commit 訊息指出了被證明正確的假設 |

階段 5 有一個例外。agent 在修正之前寫回歸測試，但只有在存在一個**正確的接縫**時：測試能以 bug 在呼叫處實際發生的方式，觸發真正的 bug 模式。當唯一可用的接縫太淺時，skill 會告訴 agent 直說，而不是寫一個帶來虛假信心的測試。缺少接縫本身就是一個發現，而 agent 會記錄它，而不是隱藏它。

## 常見問題

**它在我只想要一個直接答案的簡單問題上觸發了。**
這是這個 skill 被回報最多的問題。尤其在 GPT-5.6-Sol 上，使用者回報它會在單純描述一個問題時就觸發：「模型反而觸發了相當正式的 diagnosing-bugs skill。接著它在給我回應或建議之前，先去建構一個重現情境（常常是建一個價值有限的模擬情境）。這造成相當大的回覆延遲。」有四個不同的人在 [issue #578](https://github.com/mattpocock/skills/issues/578) 上回報了同樣的問題。被接受的修正方式是先用比較輕量的做法，只有在問題需要時才進入完整的診斷，但那個變更還沒發布。這個 skill 是針對 Claude Code 的觸發行為調整的，而一個觸發門檻比較低的[模型](https://www.aihero.dev/ai-coding-dictionary/model)會太常觸發它。在修正發布之前，變通方法是說出你要什麼（「直接回答，不要診斷」），或在你的 [harness](https://www.aihero.dev/ai-coding-dictionary/harness) 中為它停用模型觸發。

**我可以把它指向一個程式碼庫，問它效能問題在哪裡嗎？**
不行。它診斷的是一個你已經能說出來的失敗。它的效能分支是給有症狀的退化用的（建立基準量測，然後做二分搜尋，先量測、再修正），而不是一次主動的全面掃描。一個做主動版本的 skill 曾[被提出然後關閉](https://github.com/mattpocock/skills/issues/431)；目前沒有任何 skill 做這件事。

**它在寫修正之前會停下來問我嗎？**
不會。只有階段 3 有人類的檢查點：排序好的假設清單會在任何一個被測試之前先給你看，而如果你不在，agent 會依它自己的排序繼續。在觀測與修正之間沒有關卡，所以 agent 可能在你同意它的根本原因之前就開始寫程式碼。[Issue #124](https://github.com/mattpocock/skills/issues/124) 要求加入那道關卡，目前仍然開放。如果你想要它，在觸發 skill 時說出來。

**我已經對這份 bug 回報執行過 `/triage` 了。這是在重做同樣的工作嗎？**
部分是，而兩個 skill 都沒說。正如一位讀者所說：「Triage 的步驟 3 本質上就是 diagnosing-bugs 階段 1 到 2 的一個淺層、有界的版本，但兩個檔案都沒有提到對方。」Triage 做的是一次有界的「這真的是 bug 嗎、表面是什麼」的檢查；這個 skill 做的是徹底的版本。先執行 triage 並不是浪費，因為它的驗證常常能給你階段 1 大部分的原始素材。但要預期這個 skill 會完整地重做那些工作，也不要預期會有任何交叉引用告訴你這件事。

**它貼出的重現輸出會洩漏機密嗎？**
有可能。skill 要求 agent 貼出呼叫方式與它的輸出，並要求像 HAR 檔、日誌傾印與 core dump 這樣的資料。沒有任何指示告訴 agent 要清理它們。[Issue #674](https://github.com/mattpocock/skills/issues/674) 提出的正是這件事（憑證、token、cookie 與個人資料被複製到聊天、issue 或 PR 中），並提議加入一道遮蔽的護欄。它仍然開放、尚未實作。目前請把遮蔽視為你的工作，尤其是在輸出要放到任何公開的地方之前。

**我的安全掃描器把這個 skill 標記為高風險。**
Snyk 會標記它，而那是一個誤判。它是這套 skill 中唯一附帶可執行 shell 腳本（`hitl-loop.template.sh`）、同時又有執行它以及 curl 一個 dev server 的指示的 skill。一個附帶的 `.sh` 檔、執行它的指示，再加上對外的 HTTP，就足以觸發靜態掃描器。腳本本身大約是 30 行 `read -r -p` 提示，用來暫停等待人類輸入。掃描器評估的是這個 skill 可能做什麼，而不是一個已證實的漏洞。

**`/diagnose` 發生了什麼事？**
v1.0.0 把它改名為 `/diagnosing-bugs`。舊名稱已經不存在了。任何你串接了 `/diagnose` 的東西（一個包裝 skill、一個存下來的提示）都需要更新。

## 它有效的跡象

- 在提出任何一個理論之前，它會給你看一個指令以及它亮紅燈的輸出。如果理論先出現，代表這個 skill 沒有在執行。
- 它重現的失敗是你回報的那一個，而不是它在途中發現的附近另一個。
- 它在開始猜測之前會先縮小重現案例，並能告訴你為什麼需要剩下的每一部分。
- 在測試任何一個假設之前，它會給你看一份 3 到 5 個假設的排序清單，每一個都有你可以證偽的預測。
- 它加入的每一行除錯 log 都帶有一個像 `[DEBUG-a4f2]` 的標籤，而在它宣告完成時，grep 那個標籤會找不到任何東西。
- commit 或 PR 訊息指出了哪一個假設是對的。
- 當它無法用測試把 bug 鎖住時，它會直說，而不是寫一個淺層的測試。

## 它的定位

`diagnosing-bugs` 是一個隨時都能使用的獨立 skill。你在某個東西壞掉時啟動它，而它在修正與回歸測試都到位時結束。它不保存任何狀態，也不需要任何事先的設定。[ask-matt](https://aihero.dev/skills-ask-matt) 會把「某個東西壞了」指向這裡。

有兩個鄰居很重要。[retro](https://aihero.dev/skills-retro) 在它之後：修正完成後，在同一個 session 中執行它，問問什麼本可以預防這個 bug，因為此時 session 擁有比開始時更多的資訊。`diagnosing-bugs` 從不自己觸發 `retro`，因為 `retro` 是使用者觸發的。[triage](https://aihero.dev/skills-triage) 在它之前，用於以原始回報形式從別人那裡送來的 bug，並執行相同前兩個階段的淺層版本。
