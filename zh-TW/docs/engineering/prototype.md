## 它做什麼

`prototype` 撰寫**回答一個問題的、用完即丟的程式碼**：這個狀態模型感覺對嗎，或這個畫面應該長什麼樣子。問題優先，並決定你要建什麼。一個回答錯問題的原型就是浪費，不論它看起來多好。

「用完即丟」是對程式碼*寫法*的限制，而不是承諾要銷毀它。不寫測試、除了讓它能跑之外不做錯誤處理、不做抽象、不做持久化，因為這些都無助於你學到你正試圖學習的那一件事。有兩樣東西會留下來。答案進入真正的程式碼，而原型則放到 main 之外的一個分支上，作為答案的證據。

## 何時使用

輸入 `/prototype`，或者當任務適合時，[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 會自動使用它。

在你碰到一個無法透過談話解決的問題的那一刻使用它：一個你無法在腦中掌握所有邊界情況的狀態機、一個在你看到三個版本並排之前都無法想像的畫面。[拷問（grilling）](https://www.aihero.dev/ai-coding-dictionary/grilling) session 會在這種問題上變得很長。agent 換句話說，你猜測，範圍膨脹。停止拷問，做出用完即丟的版本，看看它，然後用一行字回答。如果是某個已經建好的東西行為異常、而你想知道為什麼，請使用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)；做原型是在探索要建什麼，而不是為什麼建好的東西壞了。

你也會在沒有主動選擇的情況下來到這裡。[wayfinder](https://aihero.dev/skills-wayfinder) 會在它的地圖上建立 `prototype` 決策 [ticket](https://www.aihero.dev/ai-coding-dictionary/ticket)，而你用這個 skill 來處理它們。

## 兩個分支

問題決定分支，而兩個分支產出不同的東西：

- **「這個邏輯 / 狀態模型感覺對嗎？」**：一個**可分享的單一 HTML 檔**。一個自成一體的頁面，不需要建置也不需要伺服器，任何人雙擊就能打開。它帶有一個有標籤的狀態面板，每次點擊後都會重新渲染；自由操作按鈕，可以任意順序戳戳看這個模型；以及分頁式的**引導演練**（每個分頁一個情境，各自在底下有依序要按的按鈕）。一切都以領域語言標示，所以你可以把它交給設計師、PM 或領域專家，讓他們自己試試這個模型。頁面背後的邏輯是一個小而純粹的模組（一個 reducer、一個狀態機、一組函式），裡面沒有任何 DOM 程式碼，所以你可以把驗證過的版本直接移到真正的程式碼中。
- **「這應該長什麼樣子？」**：在一個路由上的幾個**截然不同**的 UI 變體，可以從一個浮動的底部列以及 `?variant=` URL 參數切換。變體必須在結構上意見不同，而不是在顏色上；三個稍作調整的卡片格線什麼都回答不了。只要可能，它們就在一個真實的頁面中、以真實的資料與真實的資訊密度渲染，因為在一個空頁面上評估的變體看起來永遠都不錯。

兩者都把狀態保存在記憶體中、不需要任何設定就能開始，並在每一步之後給你看完整的狀態。在你發現自己開始強化其中一個的那一刻（加一個測試、接上真正的資料庫、為了一個之後可能想要的情況而通用化），你就已經不是在做原型了。

## 原型是第一手資料

一個完成的原型會留下兩樣東西，而它們去的地方不同。

你把**答案**（結論加上它解決的問題）記錄在某個永久的地方：一則 commit 訊息、一份 ADR、實作的 issue。main 在真正的程式碼中保存答案。

**原型**是答案所依據的可執行證據，你不會刪除它。它也不屬於 main，因為沒有人維護它，而它很快就會過時。所以你把它 commit 到 main 之外一個用完即丟的 `prototype/<name>` 分支，永遠不合併它，並在實作的 issue 上留下一個指向那個分支的[情境指標](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。main 保持乾淨，而下一個接手工作的人可以找到並重新執行這個原型。

## 常見問題

**等等，原型不是應該被刪掉嗎？**
已經不是了。以前是：做出來、保留答案、把程式碼丟掉。對此最強的反對意見並不是關於速度。而是*下一個 [session](https://www.aihero.dev/ai-coding-dictionary/session) 誰會接手工作，他們手上有什麼可以依據？* 一份關於原型的文字摘要，會失去讓它具說服力的那個東西。所以這個 skill 現在把原型視為一份[第一手資料](https://www.aihero.dev/ai-coding-dictionary/primary-source)。它落在 main 之外的一個 `prototype/<name>` 分支上，而實作的 issue 指向它。改變的是程式碼存放的地方，而不是紀律；它仍然永遠不會合併進 main。

**它以前會建一個終端機應用程式。那個去哪了？**
邏輯分支現在改為產出一個可分享的單一 HTML 檔。終端機應用程式只能由 clone 了 repo 並安裝了執行環境的人操作，這就排除了原型最需要聽取意見的那些人：設計師、PM、知道這個狀態模型應該代表什麼意義的領域專家。一個雙擊就能打開、被 email 轉寄之後仍然可以運作的自成一體檔案，任何人都能操作。底下的純邏輯模組沒有改變，它仍然是你要移到真正程式碼中的那一部分。

**有個 agent 叫我用 `/prototype`，但我其實應該在實作。**
這是一個已知的命名問題。一個不了解流程的 agent，會把 `prototype` 這個通用又吸引人的詞，讀成 ticket 存在之後「顯而易見的下一步」。所以即使設計已經在對話中確定了，agent 仍會指名推薦它。如果你已經知道要建什麼，下一步就是每張 ticket 執行 `/implement`。只有在某個具體的設計問題尚未解決、而且談話無法解決它時，才使用原型。

**我應該在建置任何正式功能之前，先把整個應用程式做成原型嗎（例如要展示給潛在客戶看）？**
那是一個恰好與這個 skill 同名的不同產出物。這裡的原型範圍限定在一個問題上，而「整個應用程式是什麼？」並不是一個問題。一個完整應用程式的原型沒有自然的停止點，所以它會漂移成正式的應用程式：清理那一步永遠不會發生，而在原型規則下寫的程式碼（沒有測試、沒有錯誤處理）最後會出現在使用者面前。如果你需要一個銷售 demo，就刻意把它當作 demo 來做，並明確表示其中沒有任何東西是正式版。如果你需要解決一個設計問題，就把它縮小到那個問題。

**我要怎麼在它自己的 session 中執行它？**
原型存在於它自己的目錄中，並會產生大量你不想放在提出問題那個討論串中的[情境](https://www.aihero.dev/ai-coding-dictionary/context)，所以在別的地方執行它，只把答案帶回來。使用 [handoff](https://aihero.dev/skills-handoff) 把工作移到那個 session，再把答案帶回來。

**這不是燒 token 最快的方法嗎？**
有可能，如果你為那些談話就能回答的問題做原型，或讓一個原型蔓延到整個功能。重要的比較不是 token 對零；而是 [token](https://www.aihero.dev/ai-coding-dictionary/token) 對上建出錯的狀態模型、並在它已經有正式呼叫者之後才發現。讓問題保持狹窄、讓執行保持簡短，花費就會維持在合理的比例。

## 它有效的跡象

- 你能用一句話說出這個原型存在要回答什麼問題，而且它寫在 demo 的最上方，而不只是在你腦中。
- 一個不讀程式碼的人也能操作邏輯 demo。他們打開檔案、按下某個演練分頁中的按鈕，並用自己的話描述他們看到什麼。
- 有人說「等等，這應該不可能吧」或「咦，我以為 X」。那是*想法*中的 bug，而這正是原型的用途。
- UI 變體在版面與資訊層級上意見不同，而不只是顏色與文案，而你得到的回饋是「B 的 header 配上 C 的側邊欄」。
- 它在一次坐下來的時間內就得到回答。如果一天之後你還在建它，代表問題太大了；拆分它。
- 結束時，main 中包含決策、沒有任何原型，而實作的 issue 指向仍然保存著它的那個分支。

## 它的定位

`prototype` 是一個**隨時都能使用的獨立 skill**：你用它解決一個設計問題，然後回到你的工作。另一個 skill 也會執行它。

最常執行它的 skill 是 [wayfinder](https://aihero.dev/skills-wayfinder)。一張 wayfinder 地圖由**決策 ticket** 組成，而 `prototype` 是 ticket 可以屬於的四種類型之一：在卡住的問題是「這應該長什麼樣子」或「它應該怎麼運作」、而且再多討論都無法解決時使用。當討論很模糊時，wayfinder 會做出一個能讓人反應的具體東西，而這個 skill 就負責建出那個東西。答案會解決一張原型 ticket，而地圖會把原型以資產的形式連結過去。

其他的鄰居則在那之前與之後。[grill-me](https://aihero.dev/skills-grill-me) 與 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 回答可拷問的問題；不可拷問的問題則改來這裡，而一行字的答案會回到訪談中。在下游，一個經過驗證的狀態模型或 UI 方向，會成為 [to-spec](https://aihero.dev/skills-to-spec) 已確定的輸入，後者可以把原型產出的、富含決策的程式碼片段直接內嵌，而不是用文字描述它。其他任何情況，[ask-matt](https://aihero.dev/skills-ask-matt) 都會在整套 skill 中為你指路。
