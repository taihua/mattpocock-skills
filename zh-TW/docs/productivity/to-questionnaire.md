## 它做什麼

`to-questionnaire` 把一個你無法獨自解決的決策，轉成一份**問卷**：一份 Markdown 文件，交給那位掌握你所缺少之知識的人，讓他非同步填寫，或讓你們兩人在會議中一起完成。

它拷問的是你的**寄送**，而從不是主題。針對主題的訪談毫無意義，因為正是不了解主題，你才要寫信給別人。所以它問的是你一定答得出來的兩件事（要寄給誰，以及你需要從他們那裡拿回什麼），並讓文件中的每一個問題都瞄準兩者之間的**落差（gap）**。

## 何時使用

你透過輸入 `/to-questionnaire` 來觸發它；[agent](https://www.aihero.dev/ai-coding-dictionary/agent) 不會自己去用它。

當一個決策卡在只存在於另一個人腦中的知識時使用它：一位客戶、一位領域專家、一位掌管商業規則的主管、一位不在你身邊團隊的同事。你要用哪個 skill，取決於答案在哪裡：

| 答案在…… | 使用 |
| --- | --- |
| 你自己的腦中，還沒磨利 | [grill-me](https://aihero.dev/skills-grill-me) |
| 程式碼庫中 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs) |
| 別人的腦中 | `to-questionnaire` |
| 還不在任何人的腦中，問題需要一個能讓人反應的東西 | [prototype](https://aihero.dev/skills-prototype) |

常見的情況是一場[拷問（grilling）](https://www.aihero.dev/ai-coding-dictionary/grilling) session 卡住了，因為它提出的某些問題不是你能回答的。在同一段對話中執行 `/to-questionnaire`，把那些問題帶到線下處理，然後把答案帶回來繼續。

## 是寄送，不是主題

訪談只有兩次問答，然後就停止。

- **要寄給誰？** 他們的角色、他們的專業、他們與你的關係。這決定了語氣，以及文件需要附帶多少背景。外部客戶需要被引導進入狀況；隊友則不需要。
- **你需要拿回什麼？** 你無法獨自解決的具體決策或事實。這會成為完成文件的檢查清單。你指名的每一項都會有一個瞄準它的問題。

之後的一切都是撰寫草稿。這個 skill 會把檔案寫到目前目錄的 `to-questionnaire-<slug>.md`。沒有任何設定、沒有工作區，也沒有任何東西需要配置。

## 文件

這份文件是一份**探索性問卷（discovery questionnaire）**，因為你缺乏背景，而收件人擁有它。這決定了它的形狀：

- 一行目的說明，指出依賴它的決策，以及一小段背景說明，給一位完全不了解你背景的收件人。
- 問題依**重要性由高到低**排列，並分組放在主題標題下，因為非同步的情況下你可能只有一次機會。
- 每個問題只問一件事，絕不複合，底下附一個作答區，只有在問題可能被誤解時才加上一行*為什麼這很重要*。
- 明確允許回答「我不知道」，因為一個被標示出來的不確定是有用的，而一個讀起來像事實的自信猜測則不然。
- 最後的總結提問：有沒有什麼我們沒問到、但應該知道的事？

這份文件刻意不做兩件事。它**不分支**。問題是一份扁平、分組的清單，而不是一棵「如果你回答了 A 就跳過 D 節」的樹。它也**不支援多位收件人**。一次執行為一個人產出一份文件。

## 常見問題

**它會讀取我的拷問 session，並從中擷取問題嗎？**
不是以一個獨立步驟的形式。這個 skill 沒有讀取階段。它詢問寄送的事，然後撰寫草稿。讓它在拷問 session 之後能派上用場的，是你在**同一段對話**中執行它，所以那個 [session](https://www.aihero.dev/ai-coding-dictionary/session) 已經在[情境（context）](https://www.aihero.dev/ai-coding-dictionary/context)中，撰寫草稿時就能利用它。如果你在一個新的 session 中開始，它對拷問一無所知，你就要在回答「你需要拿回什麼？」時自己再提供一次主題。

**缺少的答案並不都在同一個人身上。它能依收件人拆分嗎？**
不能。第一步問的是*那一位*收件人，單數，而這個 skill 會針對他來設定整份文件的語氣與背景。如果三個人各掌握答案的三個部分，就執行三次，每人一次。有人要求過一份能依專業或角色分派問題的文件，但那個功能沒有推出。

**問題之間有依賴關係嗎：它會根據先前的答案跳過某些段落嗎？**
不會。依賴式問題的設計曾經被探索過，但沒有推出。產出的是一份靜態文件：依主題分組、重要性由高到低、每個問題都有效。對它的反對意見是合理的。一個在拿到真實答案之前就要規劃兩三個以上問題的[模型](https://www.aihero.dev/ai-coding-dictionary/model)會規劃得很差，而一份會分支的文件，必須在每一個答案之前就規劃好所有問題。

**如果收件人也不知道怎麼辦？**
文件會告訴他直說。它明確要求「我不知道」與部分回答。一個被標示出來的不確定，比一個猜測更有價值，因為一旦回到你的情境中，一個模糊的答案和一個充滿自信的錯誤答案看起來是一模一樣的。

**它會把問卷寄到任何地方嗎（Slack、issue tracker、email）？**
不會。它在目前的目錄中寫一個 Markdown 檔，並告訴你路徑。傳遞由你負責：把它貼進一張 [ticket](https://www.aihero.dev/ai-coding-dictionary/ticket)、丟進一個 Slack 討論串、附在 email 中，或在共用螢幕上打開它並即時一起完成。這四種方式都有人手動做過。

**這不就是批次模式的 `/grill-me` 嗎？**
不是。`grill-me` 本來就以**回合**的方式提問。它一次問完整個開放問題的前緣，然後根據你的答案重新計算，所以它已經滿足了「一次給我所有問題」的需求。`to-questionnaire` 的差異在另一個軸上。它關心的是答案在誰的腦中，而不是問題如何被傳遞。要更快地自己回答，就用 `grill-me`。要從別人身上把答案拿出來，就用這個。

**我不能不用 skill，直接請 agent 做這件事嗎？**
可以，而且在它存在之前很多人都這麼做過：`OPEN_QUESTIONS.md` 檔案、寄給客戶的試算表、每個未解答的問題各開一張「需要更多資訊」的 ticket。這個 skill 為你買到兩件事：訪談永遠不會漂移到主題上，而且文件產出的形式，是非技術背景的收件人也能填寫的。如果你已經有一套行得通的內部格式，你就不需要這個。

## 它有效的跡象

- 它詢問收件人以及你需要拿回什麼，然後就不再問了。如果它開始詢問主題本身，這個 skill 就出錯了。
- 你列為「我需要拿回的東西」的每一項，都能對應到檔案中的某個問題。
- 問題讀起來是瞄準*收件人*所知道的東西，而不是把你自己的開放問題原封不動抄下來。
- 你可以把檔案交給一個不在對話中的人，他會知道自己為什麼收到它，以及要在什麼時候之前回覆。
- 回來的答案可以作為新一輪拷問的可用輸入，而不是又一組新的問題。

## 它的定位

`to-questionnaire` 是一個隨時都能使用的獨立 skill。在你自己的知識到了盡頭、下一步是去問另一個人而不是執行另一個 skill 的地方使用它。這最常發生在流程中途，當規劃卡在一件不是你能決定的事情上時。

它的鄰居是 [grill-me](https://aihero.dev/skills-grill-me)，兩者的差別在於答案存在哪裡。拷問從你身上取得答案；問卷則從別人身上取得。把拿回來的東西餵進另一輪拷問，或者，如果工作正要進入建置，就餵進 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 或 [to-spec](https://aihero.dev/skills-to-spec)。當你不確定哪個 skill 適合當下時，[ask-matt](https://aihero.dev/skills-ask-matt) 會幫你指路。
