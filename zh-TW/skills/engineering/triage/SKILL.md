# 分類（Triage）

讓專案 issue tracker 上的 issue 在一個由分類角色組成的小型狀態機中流轉。

如果這個 repo 把外部的 pull request 也視為一種請求管道（參見 issue tracker 的設定），分類也涵蓋它們：**PR 就是附帶程式碼的 issue**，使用相同的角色、相同的狀態、相同的狀態機，只有少數幾處差異在下方標註為「對 PR 而言」。依 tracker 的設定把單純的 `#42` 解析為 issue 或 PR。

分類期間發布到 issue tracker 的每一則留言或 issue，都**必須**以這段免責聲明開頭：

```
> *This was generated by AI during triage.*
```

## 參考文件

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何撰寫耐久的 agent 簡報
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知識庫如何運作

## 角色

兩個**類別**角色：

- `bug`：某個東西壞了
- `enhancement`：新功能或改善

五個**狀態**角色：

- `needs-triage`：需要維護者評估
- `needs-info`：等待回報者提供更多資訊
- `ready-for-agent`：已完整定義，可交給離線（AFK）agent
- `ready-for-human`：需要人來實作
- `wontfix`：不會處理

對 PR 而言，同樣的狀態是針對附帶的程式碼來解讀：`ready-for-agent` 代表已附上簡報，agent 應該對 diff 進行下一步；`ready-for-human` 代表已經準備好讓人合併。

每個分類過的 issue 都應該剛好帶有一個類別角色與一個狀態角色。如果狀態角色有衝突，就標示出來，並在做其他任何事之前先詢問維護者。

這些是標準的角色名稱。issue tracker 中實際使用的標籤字串可能不同。對應關係應該已經提供給你了。如果沒有，請告訴使用者執行 `/setup-matt-pocock-skills`。

狀態轉換：沒有標籤的 issue 通常先進入 `needs-triage`；從那裡再移到 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。一旦回報者回覆，`needs-info` 就回到 `needs-triage`。維護者隨時都可以覆寫；對看起來不尋常的轉換，先標示出來並在進行前詢問。

## 觸發方式

維護者觸發 `/triage`，並用自然語言描述他想要什麼。解讀這個請求並採取行動。範例：

- 「給我看任何需要我關注的東西」
- 「我們來看看 #42」（issue 或 PR）
- 「把 #42 移到 ready-for-agent」
- 「有哪些已經可以讓 agent 接手了？」

## 顯示需要關注的項目

查詢 issue tracker，呈現三個分組，最舊的排在前面：

1. **沒有標籤**：從未被分類過。
2. **`needs-triage`**：評估中。
3. **自上次分類筆記之後、回報者有新動態的 `needs-info`**：需要重新評估。

當 PR 也在範圍內時，把外部 PR 也放進這些分組，並在每一行標上 `[PR]` 或 `[issue]`。探索時只會列出*外部*的 PR（tracker 設定定義了誰算是外部），所以協作者正在進行中的 PR 不是分類的工作。這個過濾只適用於探索；被明確指名的 PR，不論作者是誰，一律進行分類。

顯示數量，以及每個項目一行摘要。讓維護者挑選。

## 分類特定的 issue 或 PR

1. **蒐集背景。** 閱讀完整的 issue 或 PR（內文、留言、標籤、作者、日期；對 PR 而言，還有 diff）。解析任何先前的分類筆記，避免重複詢問已經解決的問題。使用專案的領域詞彙表探索程式碼庫，並尊重該領域的 ADR。對程式碼庫執行兩項檢查：(a) **重複性**：依領域概念（而不只是請求的字面用詞）搜尋所請求之行為是否已有實作，並回報你找過哪些地方。如果找到了，它就是「已實作」的 `wontfix`（步驟 5）。(b) **先前的拒絕**：閱讀 `.out-of-scope/*.md`，並提出任何與這個請求相似的項目。

2. **提出建議。** 告訴維護者你建議的類別與狀態以及理由，加上一段與這個請求相關的簡短程式碼庫摘要（包括它是否已經實作）。等待指示。

3. **驗證主張。** 在任何拷問之前，先檢查這個主張是否站得住腳。對 bug 而言，依照回報者的步驟重現它。對 PR 而言，確認 diff 確實做到它所宣稱的：checkout 下來，執行相關的測試或指令。回報結果：已確認（附上程式路徑）、失敗，或細節不足（這是強烈的 `needs-info` 訊號）。經過確認的驗證能讓 agent 簡報強得多。

4. **拷問（如果需要）。** 如果這個請求需要再充實，呼叫 Skill 工具兩次，分別是 "grilling" 和 "domain-modeling"，一次一回合問題地把它拷問成形，並在決策落定時磨利領域術語、即時更新 `GLOSSARY.md` 與 ADR。

5. **套用結果：**
   - `ready-for-agent`：發布一則 agent 簡報留言（[AGENT-BRIEF.md](AGENT-BRIEF.md)）。
   - `ready-for-human`：結構與 agent 簡報相同，但註明為什麼它無法委派出去（需要判斷、需要外部存取權、設計決策、手動測試）。
   - `needs-info`：發布分類筆記（範本如下）。
   - 對於 `wontfix`，關閉 issue，留言內容依*原因*而定：
     - **已實作**：這個變更已經存在於程式碼庫中。指出它在哪裡；*不要*寫入 `.out-of-scope/`（那個知識庫是給*被拒絕*的請求，而不是已建好的）。
     - **拒絕（bug）**：給一個禮貌的說明，然後關閉。
     - **拒絕（功能增強）**：寫入 `.out-of-scope/`，在留言中連結過去，然後關閉（[OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)）。
   - `needs-triage`：套用這個角色。如果有部分進展，可以選擇留言。

## 快速覆寫狀態

如果維護者說「把 #42 移到 ready-for-agent」，就信任他並直接套用角色。確認你即將做的事（角色變更、留言、關閉），然後執行。略過拷問。如果在沒有拷問的情況下移到 `ready-for-agent`，詢問他是否要撰寫 agent 簡報。

## Needs-info 範本

```markdown
## Triage Notes

**What we've established so far（目前已確定的事）:**

- 第 1 點
- 第 2 點

**What we still need from you (@reporter)（我們仍需要你提供的）:**

- 問題 1
- 問題 2
```

把拷問期間解決的所有事項都記錄在「established so far」下，讓這些工作不會遺失。問題必須具體且可以採取行動，而不是「請提供更多資訊」。

## 接續先前的 session

如果 issue 或 PR 上已有先前的分類筆記，閱讀它們，檢查回報者是否已經回答了任何待解的問題，並在繼續之前呈現更新後的全貌。不要重複詢問已解決的問題。
