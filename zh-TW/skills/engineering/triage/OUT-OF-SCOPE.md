# 範圍外知識庫（Out-of-Scope Knowledge Base）

repo 中的 `.out-of-scope/` 目錄存放被拒絕之功能請求的持久紀錄。它有兩個目的：

1. **組織記憶**：一個功能為什麼被拒絕，讓理由不會在 issue 關閉後遺失
2. **去重複**：當一個新 issue 進來、與先前的拒絕相符時，skill 可以把先前的決策提出來，而不是重新爭論一次

## 目錄結構

```
.out-of-scope/
├── dark-mode.md
├── plugin-system.md
└── graphql-api.md
```

每個**概念**一個檔案，而不是每個 issue 一個。請求同一件事的多個 issue 歸在同一個檔案下。

## 檔案格式

檔案應該以輕鬆、易讀的風格撰寫，比較像一份簡短的設計文件，而不是一筆資料庫紀錄。使用段落、程式碼範例和舉例，讓第一次看到的人也能清楚理解且受用。

```markdown
# Dark Mode

本專案不支援深色模式或面向使用者的主題切換。

## Why this is out of scope

渲染管線假設只有一套定義在 `ThemeConfig` 中的配色。
要支援多個主題需要：

- 一個包住整個元件樹的主題 context provider
- 每個元件都要能依主題解析樣式
- 一個儲存使用者主題偏好的持久化層

這是一個重大的架構變更，與專案專注於內容創作的方向不一致。
主題是嵌入或重新散布輸出內容的下游使用者所要關心的事。

```ts
// 目前的 ThemeConfig 介面並非為執行期切換而設計：
interface ThemeConfig {
  colors: ColorPalette; // 單一配色，在建置時解析
  fonts: FontStack;
}
```

## Prior requests

- #42: "Add dark mode support"
- #87: "Night theme for accessibility"
- #134: "Dark theme option"
```

### 為檔案命名

為這個概念取一個簡短、具描述性的 kebab-case 名稱：`dark-mode.md`、`plugin-system.md`、`graphql-api.md`。名稱要夠容易辨認，讓瀏覽目錄的人不用打開檔案就能知道被拒絕的是什麼。

### 撰寫理由

理由應該有實質內容：不是「我們不想要這個」，而是為什麼。好的理由會引用：

- 專案範圍或理念（「本專案專注於 X；主題是下游的問題」）
- 技術限制（「支援這個需要 Y，這與我們的 Z 架構衝突」）
- 策略決策（「我們選擇使用 A 而不是 B，因為……」）

理由應該是持久的。避免引用暫時性的狀況（「我們現在太忙了」）；那些不是真正的拒絕，而是延後。

## 何時檢查 `.out-of-scope/`

在分類期間（步驟 1：蒐集背景），讀取 `.out-of-scope/` 中的所有檔案。評估一個新 issue 時：

- 檢查這個請求是否與既有的範圍外概念相符
- 比對的依據是概念相似度，而不是關鍵字：「night theme（夜間主題）」與 `dark-mode.md` 相符
- 如果有相符的，就提出來給維護者：「這與 `.out-of-scope/dark-mode.md` 很類似。我們之前拒絕過，因為 [理由]。你的看法還是一樣嗎？」

維護者可能會：

- **確認**：新 issue 被加入既有檔案的「Prior requests」清單，然後關閉
- **重新考慮**：範圍外檔案被刪除或更新，issue 進入正常的分類流程
- **不同意**：這些 issue 相關但不同，繼續正常的分類流程

## 何時寫入 `.out-of-scope/`

只有在一個**功能增強**（不是 bug）以 `wontfix` *被拒絕*時。這對功能增強的 PR 完全一樣適用：被拒絕的 PR 也記錄在這裡，讓同樣的請求不會以新程式碼的形式再次出現。

當某件事因為**已經實作了**而以 `wontfix` 關閉時，*不要*寫到這裡。那是已建好的功能，不是被拒絕的功能；記錄它會用虛假的拒絕汙染去重複的檢查。改為在關閉的留言中指出該功能已經存在於哪裡。

流程：

1. 維護者判定某個功能請求不在範圍內
2. 檢查是否已經存在相符的 `.out-of-scope/` 檔案
3. 如果有：把新 issue 附加到「Prior requests」清單
4. 如果沒有：建立一個新檔案，寫上概念名稱、決策、理由，以及第一筆先前請求
5. 在 issue 上發布一則留言，說明這個決策並提及 `.out-of-scope/` 檔案
6. 以 `wontfix` 標籤關閉 issue

## 更新或移除範圍外檔案

如果維護者對一個先前被拒絕的概念改變了主意：

- 刪除該 `.out-of-scope/` 檔案
- skill 不需要重新開啟舊的 issue；它們是歷史紀錄
- 觸發這次重新考慮的新 issue 進入正常的分類流程
