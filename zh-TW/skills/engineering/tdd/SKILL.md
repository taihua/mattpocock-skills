# 測試驅動開發（Test-Driven Development）

TDD 就是紅燈 → 綠燈的迴圈。這個 skill 是讓這個迴圈產出值得保留之測試的參考資料：什麼是好的測試、測試該放在哪裡、反模式，以及迴圈的規則。每一節在每一個循環都適用：在迴圈開始前與進行中查閱它們，而不是事後。

探索程式碼庫時，閱讀 `GLOSSARY.md`（如果存在），讓測試名稱與介面詞彙符合專案的領域語言，並尊重你所觸及領域中的 ADR。

## 什麼是好的測試

測試透過公開介面驗證行為，而不是實作細節。程式碼可以完全改寫；測試不應該跟著改。好的測試讀起來像一份規格：「使用者可以用有效的購物車結帳」準確告訴你存在什麼能力，而且它能撐過重構，因為它不在乎內部結構。

範例請見 [tests.md](tests.md)，mock 的準則請見 [mocking.md](mocking.md)。

## 接縫（Seam）：測試該放在哪裡

**接縫**是你進行測試的公開邊界：在不伸手進入內部的情況下觀察行為的那個介面。測試存在於接縫上，絕不針對內部。

**只在事先約定的接縫上測試。** 在寫任何測試之前，寫下要測試的接縫並與使用者確認。在未經確認的接縫上不寫任何測試。你不可能測試所有東西，所以事先約定接縫，才能讓測試的心力落在關鍵路徑與複雜邏輯上，而不是每一個邊界情況。

詢問：「公開介面是什麼？我們應該測試哪些接縫？」為每個提議的接縫附上一行說明，說明它能抓到什麼、會漏掉什麼。

當那個介面的形狀本身就有疑問時（模組有多深、接縫該放在哪裡、介面應該暴露什麼），以 "codebase-design" 呼叫 Skill 工具取得詞彙。它是 module、interface、depth、seam、adapter、leverage 與 locality 這些術語的共用來源，而且它是一份查閱用的參考，而不是要執行的一場 session。

## 反模式

- **與實作耦合**：mock 內部協作者、測試私有方法，或透過旁路驗證（直接查詢資料庫，而不是使用介面）。徵兆：你重構時測試壞了，但行為根本沒變。
- **同義反覆（Tautological）**：斷言用程式碼計算的同一種方式重新計算期望值（`expect(add(a, b)).toBe(a + b)`、用同樣方式手動推導出的快照、一個常數斷言等於它自己），所以它在構造上就一定會通過，永遠不可能與程式碼意見不同。期望值必須來自一個獨立的事實來源：一個已知正確的字面值、一個算好的範例、spec。
- **水平切片**：先寫完所有測試，再寫完所有實作。大量的測試驗證的是*想像中*的行為：你測的是東西的*形狀*，而不是面向使用者的行為，測試對真正的改變變得不敏感，而且你在理解實作之前就把測試結構定死了。改用**垂直切片**：一個測試 → 一個實作 → 重複，每一個測試都是一顆**曳光彈（tracer bullet）**，回應上一個循環教給你的東西。

## 迴圈的規則

- **先紅後綠。** 先寫會失敗的測試，然後只寫剛好足以讓它通過的程式碼。不要預想未來的測試，也不要加入臆測性的功能。
- **一次一個切片。** 每個循環一個接縫、一個測試、一個最小的實作。
- **重構不是迴圈的一部分。** 它屬於審查階段（參見 `code-review` skill），而不是紅燈 → 綠燈的實作循環。
