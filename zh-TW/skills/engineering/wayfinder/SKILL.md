一個粗略的想法來了，大到一個 agent session 裝不下，而且被迷霧包圍：從這裡到**目的地（destination）**的路還看不見。尋路（wayfinding）的重點是找到那條路，而不是朝目的地衝過去。這個 skill 把路線畫成 repo issue tracker 上的一張**共用地圖（shared map）**，然後一次一張地處理它的**決策 ticket**（解決之後會產生一個決策的問題，而不是要執行的建置切片），直到路線變得清楚。

每項工作的目的地都不同，而為它命名就是繪製地圖的第一個動作：它形塑了每一張 ticket。它可能是一份要交出去並反覆修改的 spec、一個在開始規劃前要鎖定的決策，或一個就地進行的變更，例如資料結構遷移。地圖本身與領域無關：工程工作、課程內容，任何符合這種形狀的東西都行。

## 只規劃，不執行

Wayfinder 預設是在做**規劃**：每張 ticket 解決一個決策，當路變得清楚、在有人去實際做那件事之前已經沒有任何需要決定的事時，地圖就完成了。想要直接動手做的衝動，通常就是你已經走到地圖邊緣、該交接出去的訊號。一項工作可以在它的 **Notes** 中覆寫這一點，把執行也帶進地圖本身，但如果沒有這樣的設定，就產出決策，而不是成品。

## 用名稱指稱

每張地圖與每張 ticket 都是一個 issue，所以它有一個**名稱**：它的標題。在人類會讀到的所有內容中（敘述、地圖的 Decisions-so-far），都用那個名稱來指稱它，絕不用單純的 id、編號或 slug。一整排 `#42, #43, #44` 根本看不懂；名稱一眼就能讀。id 與 URL 不會消失；名稱會包住它的連結，但它們是*藏在*名稱裡面，從不取代名稱。

## 地圖（The Map）

地圖是這個 repo issue tracker 上的單一個 issue，標上 `wayfinder:map`，是標準的產出物。它的 ticket 是地圖的子 issue。

地圖是一份**索引**，而不是一個倉庫。它列出已做出的決策，並指向存放細節的 ticket；一個決策只存在於一個地方，也就是它的 ticket，所以地圖從不重述它，只給要點並附上連結。

**地圖、它的子 ticket、阻擋關係與前緣查詢實際存放在哪裡，取決於 tracker。** issue tracker 應該已經提供給你了。如果沒有，請告訴使用者執行 `/setup-matt-pocock-skills`。查閱 tracker 文件中的「Wayfinding operations」一節，了解*這個* repo 如何表達它們。如果沒有提供任何 tracker，預設使用本地 markdown tracker。

### 地圖的內文

整張地圖的低解析度版本，每個 session 載入一次。開放中的 ticket **不會**列在這裡：它們是開放中的子 issue，透過查詢找到。

```markdown
## Destination（目的地）

<抵達這張地圖的終點是什麼樣子：這項工作正在尋路前往的 spec、決策或變更。一到兩行；每個 session 在選擇 ticket 之前都要先以它定向。>

## Notes（備註）

<領域；每個 session 都應該參考的 skill；這項工作長期的偏好>

## Decisions so far（目前為止的決策）

<!-- 索引：每張已關閉的 ticket 一行，足以判斷相關性，再點進連結查看 ticket 中保存的細節 -->

- [<已關閉 ticket 的標題>](link): <答案的一行要點>

## Not yet specified（尚未具體化）

<!-- 參見「戰爭迷霧」：範圍內、但還無法開成 ticket 的迷霧；隨著前緣推進而升級 -->

## Out of scope（範圍外）

<!-- 參見「範圍外」：被判定超出目的地的工作；已關閉，永不升級 -->
```

### Ticket

每張 ticket 都是地圖的一個**子 issue**；tracker 的 issue id 就是它的身分。它的內文就是問題，大小剛好是一個 10 萬 token 的 agent session：

```markdown
## Question（問題）

<這張 ticket 要解決的決策或調查>
```

每張 ticket 都帶有一個 `wayfinder:<type>` 標籤，是 `research`、`prototype`、`grilling`、`task` 其中之一（參見 [Ticket 類型](#ticket-類型)）。`wayfinder:` 標籤是地圖與它的 ticket 唯一會帶的標籤，絕不會有像 `ready-for-agent` 這樣的分類標籤：它們是決策，不是實作工作。

session **認領（claim）**一張 ticket 的方式，是把它指派給主導這張地圖的開發者，而且要**最先**做，在任何工作開始之前，讓同時進行的其他 session 會跳過它。那個指派者*就是*認領：一張開放、未指派的 ticket 就是未被認領。

阻擋關係使用 tracker 的**原生**依賴關係：這是必要的，因為它能在 tracker 自己的 UI 中*以視覺方式*呈現前緣，讓人類不用打開地圖就能看到哪些可以接手。只有缺乏原生阻擋功能的 tracker，才退而使用內文中的慣例寫法。當阻擋一張 ticket 的每張 ticket 都關閉時，它就**解除阻擋**；**前緣（frontier）**就是那些開放、未被阻擋、未被認領的子項，也就是已知世界的邊緣。

答案不是內文的一部分；它在解決時被記錄下來（參見[走過地圖](#走過地圖)）。解決 ticket 時建立的資產從 issue 連結過去，而不是貼進來。

## Ticket 類型

每張 ticket 不是 **HITL**（human in the loop，人在迴圈中，與一位為自己發言的人*一起*處理），就是 **AFK**（離線，由 agent 獨自驅動）。HITL ticket 只能透過那種即時交流來解決；agent 絕不代替人類扮演他那一方（一個自問自答的拷問 agent 就破壞了這一點）。

- **Research（研究）**（AFK）：閱讀文件、第三方 API 或本地資源（例如知識庫），找出某個決策正在等待的事實。由一個以 "research" 呼叫 Skill 工具的子代理來解決。在需要目前工作目錄之外的知識時使用。
- **Prototype（原型）**（HITL）：以 "prototype" 呼叫 Skill 工具，做出一個便宜、粗略、具體的東西讓人反應（一份大綱、一個粗略的版本、一個 stub，或 UI / 邏輯程式碼），藉此提高討論的精細度。把原型以資產的形式連結過去。當「它應該長什麼樣子」或「它應該怎麼運作」是關鍵問題時使用。
- **Grilling（拷問）**（HITL）：對話。預設的情況。一律呼叫 Skill 工具兩次，分別是 "grilling" 和 "domain-modeling"。
- **Task（任務）**（HITL 或 AFK）：在做出某個*決策*之前必須先完成的手動工作：沒有東西要決定、要做原型或要研究，但在它完成之前討論會被卡住。註冊某個服務以便評估它的 API、開通存取權限、搬移資料以便看清它的形狀。這是唯一一種*執行*而非決策的類型，它存在的價值在於解除某個決策的阻擋，而不是交付目的地。agent 能做到的地方就由它獨自驅動（AFK）；否則就交給人類一份精確的檢查清單（HITL）。工作完成時即解決；答案記錄做了什麼，以及之後的 ticket 所依賴的任何產生的事實（憑證存放位置、新的 URL、資料列數）。

## 戰爭迷霧（Fog of war）

地圖是*刻意*不完整的：不要畫出你還看不見的東西。在現有的 ticket 之外是**戰爭迷霧**：那些你能感覺到即將到來、但因為取決於仍未解決的問題而還無法確定的決策與調查，所構成的模糊景象。解決一張 ticket 會清除它前方的迷霧，把現在已經可以具體化的東西升級成新的 ticket，一次一張，直到通往目的地的路變得清楚、不再剩下任何 ticket。

地圖的 **Not yet specified** 一節就是寫下那片模糊景象的地方：疑似的問題、之後要回頭看的區域。它是*朝向*目的地的未探索前緣：這裡的一切都在範圍內，只是還不夠清晰到可以開成 ticket。看得多模糊或多清楚，就寫得多粗略或多完整；它同時也是一個路標，讓協作者知道這項工作正往哪裡去。

**是迷霧還是 ticket？** 判準是你現在能不能精確地說出這個問題，*而不是*你現在能不能回答它。

- **開成 ticket**：當問題已經很清晰時，即使它被阻擋、你還不能處理它。
- **放進 Not yet specified**：當你還無法把它說得那麼清晰時。不要預先把迷霧切成 ticket 大小的碎片：迷霧比 ticket 粗糙，一片迷霧在前緣到達時，可能升級成好幾張 ticket，也可能一張都沒有。

**Not yet specified** 不包含已經決定的事（Decisions so far）、已經是現有 ticket 的事，以及範圍外的事（下一節）。

## 範圍外（Out of scope）

迷霧只會*朝向*目的地聚集。目的地決定了範圍，所以超出它的工作就是**範圍外**：它不是迷霧，也不屬於 **Not yet specified**。它在地圖上有自己的 **Out of scope** 一節：你有意識地從*這項*工作中排除的工作。讓它落在這裡的是範圍，而不是清晰度。

範圍外的工作永遠不會升級（前緣止於目的地），所以只有在目的地被重新劃定時它才會回來，而且是以一項新的工作回來，而不是接續原本的。

把某件事判定為範圍外是一個界定範圍的動作，而不是路線上的一步。當一張已經存在的 ticket 後來被發現位於目的地之外時（繪製地圖時被誤劃進範圍，或被某個解決結果暴露出來），**關閉它**（已關閉的 ticket 明確地不在前緣上），並在 **Out of scope** 一節留下一行：要點加上它為什麼在範圍外，並連結到已關閉的 ticket。它不放進 **Decisions so far**，因為那裡記錄的是實際走過的路線；範圍邊界不是路線上的一步。

## 觸發方式

兩種模式。不論哪一種，**每個 session 絕不解決超過一張 ticket**，研究 ticket 例外。

### 繪製地圖

使用者帶著一個粗略的想法觸發。

1. **為目的地命名。** 呼叫 Skill 工具兩次，分別是 "grilling" 和 "domain-modeling"，確定這張地圖正在尋路前往的是什麼：spec、決策或變更。目的地決定了範圍，所以要最先確定。
2. **描繪前緣。** 再拷問一次，這次採**廣度優先**：在整個空間中展開，而不是深入任何一條線，找出開放中的決策以及現在就能採取的第一步。**如果這沒有揭露任何迷霧**（通往目的地的路已經很清楚，整趟旅程小到一個 session 就能完成），你就不需要地圖。停下來，詢問使用者想如何進行。
3. **建立地圖**（標籤 `wayfinder:map`）：填好 Destination 與 Notes，Decisions-so-far 留空，把迷霧粗略畫進 **Not yet specified**。
4. **建立你現在能具體化的 ticket**，作為地圖的子 issue，然後在**第二輪**接上阻擋關係（issue 需要先有 id 才能互相引用）。交叉引用也在那一輪寫，使用真實的 id：一個佔位用的 `#<n>` 會自動連結到一個無關的 issue。接線會把它們分成前緣與被阻擋的兩類；所有你還無法具體化的東西都留在迷霧中：也就是 **Not yet specified** 一節。
5. **派出研究子代理。** 對你剛建立的每一張 `research` ticket，啟動一個使用全新 context window 的子代理，以 "research" 呼叫 Skill 工具來平行解決它，把它的發現保存在一個用完即丟的 `research/<name>` 分支上，並從 ticket 放一個指向它的情境指標。推送這個分支，但不開 PR：它永遠不會被合併。
6. 停止：繪製地圖是一個 session 的工作；它不手動解決任何東西。

### 走過地圖

使用者帶著一張地圖（URL 或編號）觸發。ticket 是**選填**的：沒有指定的話，由你挑選下一個決策，而不是使用者。

1. 載入**地圖**：低解析度的景象，而不是每一張 ticket 的內文。
2. 選擇 ticket。如果使用者指定了一張，就用它。否則依序取前緣的第一張 ticket。**認領它**：在任何工作開始之前，把它指派給你自己。
3. 依照它的 `wayfinder:<type>` 標籤所指名的類型來解決它（參見 [Ticket 類型](#ticket-類型)）。讀標籤，而不只是讀內文：內文從不說明類型。**視需要放大檢視**：依需要取得任何相關或已關閉 ticket 的完整內文；為 `## Notes` 區塊所指名的任何 skill 呼叫 Skill 工具。如果有疑慮，就呼叫 Skill 工具兩次，分別是 "grilling" 和 "domain-modeling"。
4. 記錄解決結果：把答案發布為一則**解決留言**、**關閉**這個 issue，並在地圖的 Decisions-so-far **附加一個情境指標**。
5. 加入新浮現的 ticket（先建立、再接線）；把答案已經讓它可以具體化的迷霧升級，並把每一片升級過的迷霧從 **Not yet specified** 中清除，讓它只以新 ticket 的形式存在。如果答案揭示某張 ticket（這張或另一張）位於目的地之外，就**判定它為範圍外**，而不是在路線上解決它。如果這個決策使地圖的其他部分失效，就更新或刪除那些 ticket。

使用者可能會平行執行未被阻擋的 ticket，所以要預期其他 session 可能同時在編輯 tracker。
