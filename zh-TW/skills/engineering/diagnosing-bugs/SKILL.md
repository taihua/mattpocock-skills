# 診斷 Bug（Diagnosing Bugs）

一套處理棘手 bug 的紀律。只有在有明確理由時才跳過階段。

探索程式碼庫時，閱讀 `GLOSSARY.md`（如果存在），以對相關模組建立清楚的心智模型，並查看你所觸及領域中的 ADR。

## 遮蔽機密

這個 skill 會要你展示指令、輸出與擷取到的資料。**先遮蔽每一個機密**：在它的位置寫上 `<REDACTED>`。讓迴圈讀取環境變數，這樣憑證會留在環境中，而不會出現在你展示的內容裡。擷取到的資料會帶有認證標頭：只引用帶有訊號的那幾行。

如果遮蔽後的輸出不足以診斷 bug，就直說並詢問使用者。

## 階段 1：建立回饋迴圈

**這就是這個 skill 的核心。** 其他一切都是機械性的。如果你有一個針對這個 bug 的**緊密（tight）**通過/失敗訊號（一個會在*這個* bug 上亮紅燈的訊號），你就會找到原因；二分搜尋、假設驗證與觀測都只是在消耗這個訊號。如果你沒有，盯著程式碼看再久也救不了你。

在這裡投入不成比例的心力。**積極一點。有創意一點。拒絕放棄。**

### 建立迴圈的方法，大致依此順序

1. 在能觸及 bug 的任何接縫上寫一個**會失敗的測試**：單元、整合、端到端。
2. 對執行中的 dev server 執行 **Curl / HTTP 腳本**。
3. 以固定的輸入做 **CLI 呼叫**，把 stdout 與已知正確的快照做 diff。
4. **無頭瀏覽器腳本**（Playwright / Puppeteer），操作 UI 並對 DOM、主控台或網路做斷言。
5. **重播擷取到的追蹤資料。** 把真實的網路請求、payload 或事件日誌存到磁碟；單獨透過那條程式路徑重播它。
6. **用完即丟的測試架（harness）。** 啟動系統的最小子集（一個服務、mock 掉的依賴），用單一個函式呼叫就能觸發 bug 的程式路徑。
7. **性質測試 / 模糊測試迴圈。** 如果 bug 是「有時候輸出錯誤」，就跑 1000 個隨機輸入並尋找失敗模式。
8. **二分搜尋測試架。** 如果 bug 出現在兩個已知狀態之間（commit、資料集、版本），就把「以狀態 X 啟動、檢查、重複」自動化，讓你可以用 `git bisect run` 跑它。
9. **差異比對迴圈。** 把同樣的輸入同時跑過舊版與新版（或兩種設定），然後比對輸出。
10. **人在迴圈中（HITL）的 bash 腳本。** 最後手段。如果一定要有人去點擊，就用 `scripts/hitl-loop.template.sh` 來引導*那個人*，讓迴圈仍然是結構化的。擷取到的輸出會回饋給你。

建立對的回饋迴圈，bug 就修好了 90%。

### 收緊迴圈

把迴圈當成一個產品。一旦你有了*一個*迴圈，就**收緊**它：

- 我能讓它更快嗎？（快取準備工作、略過無關的初始化、縮小測試範圍。）
- 我能讓訊號更銳利嗎？（對具體的症狀做斷言，而不是「沒有當掉」。）
- 我能讓它更具確定性嗎？（固定時間、設定亂數種子、隔離檔案系統、凍結網路。）

一個 30 秒、時好時壞的迴圈，只比沒有迴圈好一點點；一個 2 秒、確定性的迴圈才是緊密的，是除錯的超能力。

### 非確定性的 bug

目標不是乾淨的重現，而是**更高的重現率**。把觸發條件跑 100 次、平行化、加壓、縮小時序窗口、注入 sleep。50% 機率出現的 bug 可以除錯；1% 的不行，所以要持續提高重現率，直到可以除錯為止。

### 當你真的無法建立迴圈時

停下來並明確說出來。列出你嘗試過的方法。向使用者要求：(a) 存取能重現它的環境，(b) 一份遮蔽過的擷取資料（HAR 檔、日誌傾印、core dump、帶時間戳的螢幕錄影），或 (c) 加入暫時性正式環境觀測的許可。沒有迴圈就*不要*進入提出假設的階段。

### 完成條件：一個會亮紅燈的緊密迴圈

當迴圈是**緊密的**且**能亮紅燈**時，階段 1 就完成了：你能說出**一個指令**（一個腳本路徑、一次測試呼叫、一個 curl），它是你**已經執行過至少一次**的（展示呼叫方式與它的輸出，並遮蔽機密），而且它：

- [ ] **能亮紅燈**：它驅動實際的 bug 程式路徑，並對**使用者所描述的確切症狀**做斷言，所以它能在這個 bug 上亮紅燈，並在修好後轉綠。不是「執行時沒有錯誤」；它必須能*抓到這個特定的 bug*。
- [ ] **具確定性**：每次執行的判定都一樣（時好時壞的 bug：依上述，有一個固定且高的重現率）。
- [ ] **快速**：幾秒鐘，而不是幾分鐘。
- [ ] **agent 可執行**：你可以在無人看管的情況下執行它；只能透過 `scripts/hitl-loop.template.sh` 讓人參與迴圈。

如果你發現自己在這個指令存在之前就在讀程式碼建立理論，**停下來：直接跳到假設，正是這個 skill 要防止的失敗。** 沒有能亮紅燈的指令，就沒有階段 2。

## 階段 2：重現 + 最小化

執行迴圈。看著它在 bug 出現時亮紅燈。

確認：

- [ ] 迴圈產生的是**使用者**描述的失敗模式，而不是剛好在附近的另一個失敗。錯的 bug = 錯的修正。
- [ ] 這個失敗在多次執行中都能重現（或者，對於非確定性的 bug，能以足夠高的比率重現，足以拿來除錯）。
- [ ] 你已經擷取到確切的症狀（錯誤訊息、錯誤的輸出、緩慢的時間），讓後面的階段能驗證修正確實解決了它。

### 最小化

一旦它亮紅燈，就把重現案例縮小到**仍然會亮紅燈的最小情境**。**一次一個**地刪減輸入、呼叫者、設定、資料與步驟，每刪一次就重新執行迴圈，只保留對這個失敗有承重作用的部分。

為什麼要這麼麻煩：最小化的重現案例能縮小階段 3 的假設空間（剩下可懷疑的活動部件更少），並在階段 5 成為乾淨的回歸測試。

當**剩下的每個元素都有承重作用**時就完成了：移除其中任何一個都會讓迴圈轉綠。

在你完成重現**以及**最小化之前，不要往下進行。

## 階段 3：提出假設

在測試任何假設之前，先產生 **3 到 5 個排序過的假設**。只產生一個假設，會讓你錨定在第一個看似合理的想法上。

每個假設都必須是**可證偽的**：說明它做出的預測。

> 格式：「如果 <X> 是原因，那麼 <改變 Y> 會讓 bug 消失 / <改變 Z> 會讓它更嚴重。」

如果你說不出預測，這個假設只是一種感覺：丟掉它或把它磨利。

**在測試之前，把排序過的清單給使用者看。** 他們常常有能立刻重新排序的領域知識（「我們剛剛部署了一個跟 #3 有關的變更」），或知道哪些假設他們已經排除過了。便宜的檢查點，省下大量時間。不要因此卡住；如果使用者不在，就照你的排序繼續。

## 階段 4：加入觀測

每一個探針都必須對應到階段 3 中某個具體的預測。**一次只改變一個變數。**

工具的偏好順序：

1. 如果環境支援，使用**除錯器 / REPL 檢查**。一個中斷點勝過十行 log。
2. 在能區分各個假設的邊界上加入**有目標的 log**。
3. 絕不要「什麼都 log 然後用 grep 找」。

**為每一行除錯 log 加上標籤**，使用一個獨特的前綴，例如 `[DEBUG-a4f2]`。最後的清理就只需要一次 grep。沒有標籤的 log 會殘留下來；有標籤的 log 才會被清掉。

**效能分支。** 對於效能退化，log 通常是錯的工具。改為：先建立一個基準量測（計時測試架、`performance.now()`、profiler、查詢計畫），然後做二分搜尋。先量測，再修正。

## 階段 5：修正 + 回歸測試

**在修正之前**寫回歸測試，但只有在它有一個**正確的接縫**時才這麼做。

正確的接縫，是指測試能以 bug 在呼叫處實際發生的方式，觸發**真正的 bug 模式**。如果唯一可用的接縫太淺（bug 需要多個呼叫者，測試卻只有單一呼叫者；單元測試無法重現觸發 bug 的那條呼叫鏈），在那裡的回歸測試只會帶來虛假的信心。

**如果不存在正確的接縫，這件事本身就是一個發現。** 記下來。是程式碼庫的架構讓這個 bug 無法被鎖住。把這件事標示出來，留給下一個階段。

如果存在正確的接縫：

1. 把最小化的重現案例變成那個接縫上的一個失敗測試。
2. 看著它失敗。如果你是透過修改程式碼或測試資料來強制它亮紅燈，在信任它之前，先與原始副本做 `diff`，證明那個修改確實生效了。
3. 套用修正。
4. 看著它通過。
5. 對原始（未最小化）的情境重新執行階段 1 的回饋迴圈。

## 階段 6：清理

在宣告完成之前必須做到：

- [ ] 原始的重現案例不再重現（重新執行階段 1 的迴圈）
- [ ] 回歸測試通過（或已記錄缺少接縫這件事）
- [ ] 所有 `[DEBUG-...]` 觀測都已移除（用 `grep` 搜尋前綴）
- [ ] 用完即丟的原型已刪除（或移到明確標示的除錯位置）
- [ ] 在 commit 或 PR 訊息中說明最後被證明正確的假設，讓下一位除錯的人能學到
