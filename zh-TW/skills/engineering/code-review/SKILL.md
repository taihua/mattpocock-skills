針對 `HEAD` 與使用者提供的某個固定點之間的 diff 進行雙軸審查：

- **Standards（規範）**：程式碼是否符合這個 repo 文件化的程式碼規範？
- **Spec（規格）**：程式碼是否忠實實作了原始的 issue 或 spec？

兩個軸都以**平行的子代理**執行，讓它們不會互相汙染彼此的情境，然後由這個 skill 彙整它們的發現。每個子代理都以全新的 context window 啟動。

issue tracker 應該已經提供給你了。如果沒有，請告訴使用者執行 `/setup-matt-pocock-skills`。

## 流程

### 1. 釘住固定點

使用者說的是什麼，固定點就是什麼（commit SHA、分支名稱、tag、`main`、`HEAD~5` 等等）。如果他沒有指定，就詢問。

記下一次 diff 指令：`git diff <fixed-point>...HEAD`（三個點，所以比較的對象是 merge-base）。同時透過 `git log <fixed-point>..HEAD --oneline` 記下 commit 清單。

在進一步之前，確認固定點可以被解析（`git rev-parse <fixed-point>`），而且 diff 不是空的。錯誤的 ref 或空的 diff 應該在這裡就失敗，而不是在兩個平行的子代理裡面才失敗。

### 2. 找出 spec 的來源

依以下順序尋找原始的 spec：

1. commit 訊息中的 issue 引用（`#123`、`Closes #45`、GitLab 的 `!67` 等），透過 tracker 文件中的流程取得。
2. 使用者以參數傳入的路徑。
3. 在 `docs/`、`specs/` 或 `.scratch/` 下，與分支名稱或功能相符的 spec 檔案。
4. 如果什麼都找不到，就詢問使用者 spec 在哪裡。如果他說沒有，**Spec** 子代理就會跳過，並回報「no spec available（沒有可用的 spec）」。

### 3. 找出規範的來源

在 repo 中搜尋每一個說明程式碼該怎麼寫的檔案。當 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md` 存在時，它們必須在清單上。

在 repo 文件化的內容之上，Standards 軸永遠帶著下方的**壞味道基準（smell baseline）**：一組固定的 Fowler 程式碼壞味道（出自《_Refactoring_（重構）》第 3 章），即使 repo 沒有任何文件化的規範也適用。有兩條規則約束它：

- **以 repo 為準。** 文件化的 repo 規範永遠優先；當它認可某件基準會標記的事情時，就壓下那個壞味道。
- **永遠是判斷題。** 每一個壞味道都是一個帶標籤的經驗法則（「possible Feature Envy（可能有依戀情結）」），而不是硬性違規。就像這裡的任何規範一樣，略過任何工具已經強制執行的東西。

每個壞味道的寫法是*它是什麼* → *怎麼修*；拿它去比對 diff：

- **Mysterious Name（神秘命名）**：一個函式、變數或型別的名稱沒有揭示它做什麼或存什麼。→ 重新命名；如果想不出誠實的名稱，代表設計本身很模糊。
- **Duplicated Code（重複程式碼）**：同樣的邏輯形狀出現在這次變更的不只一個 hunk 或檔案中。→ 抽出共用的形狀，讓兩邊都呼叫它。
- **Feature Envy（依戀情結）**：一個方法伸手去存取另一個物件的資料，多過它自己的資料。→ 把方法移到它所依戀的資料上。
- **Data Clumps（資料泥團）**：同樣的幾個欄位或參數總是一起出現（一個想要誕生的型別）。→ 把它們包成一個型別，傳遞那個型別。
- **Primitive Obsession（基本型別偏執）**：用一個基本型別或字串代表一個值得擁有自己型別的領域概念。→ 給這個概念一個專屬的小型別。
- **Repeated Switches（重複的 switch）**：同樣針對同一個型別的 `switch` 或 `if` 串，在這次變更中重複出現。→ 用多型取代，或用一個兩處共用的 map。
- **Shotgun Surgery（散彈式修改）**：一個邏輯上的變更，迫使 diff 中許多檔案都有零散的修改。→ 把一起變動的東西集中到一個模組。
- **Divergent Change（發散式變化）**：一個檔案或模組因為好幾個不相關的理由被修改。→ 拆開，讓每個模組只因一個理由而變。
- **Speculative Generality（夸夸其談的通用性）**：為了 spec 中不存在的需求而加入的抽象、參數或 hook。→ 刪掉；內嵌回去，直到出現真正的需求。
- **Message Chains（過長的訊息鏈）**：呼叫者不應依賴的冗長 `a.b().c().d()` 導航。→ 把這段走訪藏到第一個物件的一個方法後面。
- **Middle Man（中間人）**：一個大多只是往下委派的類別或函式。→ 拿掉它，直接呼叫真正的目標。
- **Refused Bequest（被拒絕的遺贈）**：一個子類別或實作者忽略或覆寫了它繼承的大部分東西。→ 拿掉繼承，改用組合。

### 4. 平行派出兩個子代理

同時發出兩個子代理的呼叫，在前景執行，並彙整它們回傳的報告。

**Standards 子代理的提示**應包含：

- 完整的 diff 指令與 commit 清單。
- 你在步驟 3 找到的規範來源檔案清單，**加上步驟 3 的壞味道基準**，完整貼上（子代理沒有其他管道可以取得它）。
- 任務簡述：「依檔案或 hunk（如果相關）回報：(a) diff 違反文件化規範的每一處：引用該規範（檔案 + 規則）；以及 (b) 你發現的任何基準壞味道：說出它的名稱並引用該 hunk。區分硬性違規與判斷題：違反文件化規範可以是硬性的，但基準壞味道永遠是判斷題，而且文件化的 repo 規範優先於基準。略過任何工具會強制執行的東西。400 字以內。」

**Spec 子代理的提示**應包含：

- diff 指令與 commit 清單。
- spec 的路徑或已取得的內容。
- 任務簡述：「回報：(a) spec 要求但缺漏或只做了一部分的需求；(b) diff 中沒被要求的行為（範圍蔓延）；(c) 看起來已實作、但實作方式看起來是錯的需求。每一項發現都引用對應的 spec 內容。400 字以內。」

如果沒有 spec，就跳過 Spec 子代理，並在最終報告中註明。

### 5. 彙整

把兩份報告分別放在 `## Standards` 與 `## Spec` 標題下呈現，逐字照搬或稍加整理。*不要*合併或重新排序發現，因為兩個軸是刻意分開的（參見「為什麼要兩個軸」）。

最後用一行總結：每個軸的發現總數，以及*每個軸之內*最嚴重的問題（如果有的話）。不要在兩個軸之間選出單一個贏家：那正是分開兩軸所要防止的重新排序。

## 為什麼要兩個軸

一個變更可能通過其中一軸、卻沒通過另一軸：

- 程式碼遵循了每一條規範，但實作了錯的東西 → **Standards 通過，Spec 失敗。**
- 程式碼完全做到了 issue 的要求，但破壞了專案的慣例 → **Spec 通過，Standards 失敗。**

分開回報能防止其中一軸掩蓋另一軸。
