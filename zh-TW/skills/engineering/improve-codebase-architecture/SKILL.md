# 改善程式碼庫架構（Improve Codebase Architecture）

找出架構上的摩擦點，並提出**加深的機會（deepening opportunities）**：把淺模組變成深模組的重構。目標是可測試性與 AI 可導覽性。

這個指令以專案的領域模型為*依據*，並建立在一套共用的設計詞彙之上：

- 以 "codebase-design" 呼叫 Skill 工具，取得架構詞彙（**module**、**interface**、**depth**、**seam**、**adapter**、**leverage**、**locality**）及其原則（刪除測試、「介面就是測試面」、「一個 adapter = 假想的接縫，兩個 = 真正的接縫」）。在每一項建議中精確使用這些術語，不要偏離成「component」、「service」、「API」或「boundary」。
- `GLOSSARY.md` 中的領域語言為好的接縫提供名稱；`docs/adr/` 中的 ADR 記錄了這個指令不應該重新爭論的決策。

## 流程

### 1. 探索

**掃描之前先劃定範圍：YAGNI。** 加深一個模組的回報，在於讓未來對它的修改變得更容易，所以要額外重視程式碼庫中最近有變動的部分。在看之前，先決定要看*哪裡*：

- 如果使用者指定了方向（某個模組、某個子系統、某個痛點），就採用它，並略過下面的推斷。
- 否則，往回翻一大段 commit 歷史（`git log --oneline`），找出程式碼庫的熱點，也就是那些反覆出現的檔案與區域，讓這些路徑優先吸引你的注意。如果變更很分散、沒有明顯的熱點，就把網撒得更大。

先閱讀專案的領域詞彙表（`GLOSSARY.md`），以及你所觸及領域中的任何 ADR。

接著派出一個使用全新 context window 的子代理去走訪程式碼庫。不要遵循僵化的經驗法則；有機地探索，並記下你感受到摩擦的地方：

- 在哪裡，理解一個概念需要在許多小模組之間跳來跳去？
- 在哪裡，模組是**淺**的，介面幾乎和實作一樣複雜？
- 在哪裡，純函式只是為了可測試性而被抽出來，但真正的 bug 藏在它們被呼叫的方式中（沒有**局部性**）？
- 在哪裡，緊密耦合的模組跨過它們的接縫洩漏？
- 程式碼庫的哪些部分沒有測試，或很難透過目前的介面測試？

對任何你懷疑是淺的東西套用**刪除測試**：刪掉它會讓複雜度集中，還是只是讓它搬家？「是的，會集中」就是你要的訊號。

### 2. 以 HTML 報告呈現候選項目

把一個自成一體的 HTML 檔寫到作業系統的暫存目錄，這樣就不會有任何東西落進 repo。從 `$TMPDIR` 解析暫存目錄，沒有的話退回 `/tmp`（Windows 上是 `%TEMP%`），並寫到 `<tmpdir>/architecture-review-<timestamp>.html`，讓每次執行都產生一個新檔案。為使用者打開它（Linux 上用 `xdg-open <path>`、macOS 上用 `open <path>`、Windows 上用 `start <path>`），並告訴他絕對路徑。

報告使用 **透過 CDN 載入的 Tailwind** 處理版面與樣式，並在圖、流程或序列能可靠傳達結構的地方，使用 **透過 CDN 載入的 Mermaid** 繪製圖表。把 Mermaid 與手工打造的 CSS/SVG 視覺混用：當關係是圖狀時（呼叫圖、依賴、序列）用 Mermaid；當你想要比較具編輯風格的東西時（質量圖、剖面圖、收合動畫）用手工的 div/SVG。每個候選項目都有一個**之前 / 之後的視覺化**。要視覺化。

為每個候選項目渲染一張卡片，包含：

- **檔案**：涉及哪些檔案或模組
- **問題**：為什麼目前的架構造成摩擦
- **解法**：以淺白的英文描述會改變什麼
- **好處**：以局部性與槓桿來解釋，以及測試會如何改善
- **之前 / 之後的圖表**：並排、客製繪製，說明淺薄之處與加深的方式
- **建議強度**：`Strong`、`Worth exploring`、`Speculative` 其中之一，以徽章呈現

在報告最後加上一個**首要建議（Top recommendation）**區塊：你會先處理哪個候選項目，以及為什麼。

**領域使用 GLOSSARY.md 的詞彙，架構使用 `/codebase-design` 的詞彙。** 如果 `GLOSSARY.md` 定義了「Order」，就說「Order 進件模組」，而不是「FooBarHandler」，也不是「Order service」。

**ADR 衝突**：如果某個候選項目與既有的 ADR 矛盾，只有在摩擦真實到值得重新檢視該 ADR 時才提出來。在卡片中清楚標示（例如一個警告提示框：*「與 ADR-0007 矛盾，但值得重新討論，因為……」*）。不要列出每一個 ADR 禁止的理論性重構。

完整的 HTML 骨架、圖表模式與樣式指引，請參見 [HTML-REPORT.md](HTML-REPORT.md)。

*還不要*提出介面。檔案寫好之後，詢問使用者：「你想探索其中哪一個？」

### 3. 拷問迴圈

使用者挑選一個候選項目後，以 "grilling" 呼叫 Skill 工具，與他一起走過決策樹：限制、依賴、加深後模組的形狀、接縫後面放什麼、哪些測試會留下來。

副作用在決策成形時即時發生；以 "domain-modeling" 呼叫 Skill 工具，讓領域模型隨著進行保持最新：

- **用一個不在 `GLOSSARY.md` 中的概念來為加深後的模組命名？** 把這個術語加到 `GLOSSARY.md`。如果檔案不存在，就延遲建立它。
- **在對話中磨利了一個模糊的術語？** 當場更新 `GLOSSARY.md`。
- **使用者以一個具承重作用的理由否決了這個候選項目？** 提議寫一份 ADR，措辭為：*「要不要我把這個記錄成 ADR，讓未來的架構審查不會再建議它？」* 只有在未來的探索者確實需要這個理由、才能避免再次建議同一件事時才提議；略過暫時性的理由（「現在不值得」）與不言自明的理由。
- **想為加深後的模組探索替代介面？** 以 "codebase-design" 呼叫 Skill 工具，並使用它的「設計兩次（design-it-twice）」平行子代理模式。
