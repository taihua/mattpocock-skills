# 問 Matt（Ask Matt）

你不可能記得每一個 skill，所以就問吧。

在說明某個 skill 做什麼、或建議跳過某個步驟之前，先讀那個 skill 的 SKILL.md：這裡的摘要只是用來辨別方向。

**流程（flow）**是一條穿過各個 skill 的路徑。大多數路徑都沿著一條**主流程（main flow）**前進，另外有兩條**匝道（on-ramp）**會匯入它。其他的則是獨立的 skill，或在底層運作的詞彙層。

## 主流程：想法 → 出貨

大多數工作走的路線。你有一個想法，想把它做出來。

1. **`/grill-with-docs`** 透過訪談把想法磨利。只要你是**在一個工作目錄中工作**，就從這裡開始：它是有狀態的，會把學到的東西保存在 `GLOSSARY.md` 與 ADR 中。（沒有工作目錄？改用 `/grill-me`，在「獨立 skill」中介紹。兩者都執行同一個 `/grilling` 基本元件；`grill-with-docs` 是會留下書面紀錄的那一個，所以只要有 repo 可以留下紀錄，它就是兩者中較好的選擇。）
2. **分支：每個問題都能在對話中解決嗎？** 如果某個問題需要一個可執行的答案（狀態、商業邏輯、一個你必須親眼看到的 UI），就繞道去做原型，並在雙向都以 **`/handoff`** 銜接（原型存在於它自己的目錄中，這正是 `/handoff` 的用途；參見「階段邊界」）：
   - 先 **`/handoff`** 出去，然後針對那個檔案開一個新的 session，
   - 用 **`/prototype`** 以用完即丟的程式碼回答問題，
   - 再 **`/handoff`** 把你學到的東西帶回來，並從原本的想法討論串中引用它。
3. **分支：這是需要多個 session 的建置嗎？**
   - **是** → **`/to-spec`**（把討論串轉成一份 spec），接著用 **`/to-tickets`** 把它拆成曳光彈式的 ticket，每張都宣告它的**阻擋關係**。然後用以下兩種方式之一處理 ticket：
     - 每張 ticket 用一次 **`/implement`**，**每張之間都 `/clear` 清空情境**。在本地 tracker 上，那就是 `.scratch/<feature>/issues/` 下每張 ticket 一個檔案，依阻擋者優先的順序手動處理；在真正的 tracker 上，阻擋關係會變成原生的阻擋連結，所以任何阻擋者都已完成的 ticket 都可以接手。每張 ticket 都自成一體，所以上一張的情境可以丟掉。
     - 用 **`/implement-spec`** 一次執行完整份 spec。它把 ticket 讀成一張**任務圖**，在已就緒的**前緣**上平行執行實作子代理，並把一切都落在一個**整合分支**上。當你寧可統籌整個建置、而不是自己逐張驅動 ticket 時使用。
   - **否** → 直接在這裡、在同一個 context window 中執行 **`/implement`**。

   不論哪一種，程式碼都透過驅動 **`/tdd`**（一次一個紅燈、綠燈切片）來建立，並以 **`/code-review`** 收尾，對 diff 進行雙軸（Standards + Spec）審查。`/implement` 每張 ticket 都會執行這兩者；`/implement-spec` 的每個實作者各自驅動 `/tdd`，最後對整合分支執行一次 `/code-review`。當你只想以測試先行的方式建立一個具體行為、不需要完整的 spec 時，就單獨使用 **`/tdd`**；當你想針對某個固定點審查一個分支或 PR 時，就單獨使用 **`/code-review`**。

   當工作以 pull request 的形式提交時，**`/pr`** 會形塑它的內文：能呈現變更的最小視覺化、證明它可運作的前後對比證據，以及單向門或雙向門的判斷。它是模型觸發的，所以 agent 只要撰寫 PR 就會使用它。

4. **`/retro`** 讓迴圈閉合。在一次建置之後，尤其是出了狀況的那種，它會回顧這個 session，並建議如何改變 agent 的**環境**，而不是程式碼：導覽指標、自動化檢查、`/code-review` 所執行的程式碼規範、引導檔案、工具。機械性的錯誤變成確定性的檢查；判斷題變成程式碼規範。下一次建置就從一個更好的環境開始。

### 情境衛生（Context hygiene）

讓步驟 1 到 3 留在**同一個不中斷的 context window** 中（在 `/to-tickets` 之前都不要壓縮或清空），讓拷問、spec 與 ticket 都建立在同一套思考之上。之後每一次 `/implement` 都從頭開始，以 ticket 為依據工作。在 `/retro` 所要回顧的那個 session 中、在你清空之前執行它；清空之後，就改為把它指向那個 session 的紀錄。

這件事的上限是**[聰明區（smart zone）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：模型仍能敏銳推理的那段視窗（在最先進的模型上約 15 萬 token）。如果一個 session 在 `/to-tickets` 之前就快要到達這個上限，不要在品質下降的狀態下硬撐；在最近的階段邊界執行 `/compact` 然後繼續（參見「階段邊界」）。

## 匝道

會產生工作、然後匯入主流程的起始情境。

- **Bug 與請求越積越多** → **`/triage`**。它讓 issue 在分類角色之間流轉，並產出 agent 可直接處理的 issue，之後由 **`/implement`** 接手。

  分類只用於**不是你自己建立的** issue：bug 回報、外部進來的功能請求，任何以原始狀態送達的東西。`/to-tickets` 產出的 ticket 已經是 agent 可直接處理的，所以**不要分類它們**。

- **某個東西壞了** → **`/diagnosing-bugs`**。用於棘手的那種：第一眼看不出來的 bug、時好時壞的不穩定問題、在兩個已知正常的狀態之間悄悄出現的退化。它在擁有一個**緊密的回饋迴圈**（一個已經會在*這個* bug 上亮紅燈的指令）之前拒絕提出理論，然後連同回歸測試一起修正。修正完成後，在同一個 session 中執行 **`/retro`**，問問什麼本可以預防這個 bug；如果真正的發現是沒有好的接縫可以把它鎖住，那就是 **`/improve-codebase-architecture`** 的工作。

- **一項巨大、迷霧重重的工作：一個全新專案或一個龐大的功能建置，大到一個 session 裝不下** → **`/wayfinder`**，這裡最耗費腦力的流程。當從這裡到目的地的路還看不見時，它會在 issue tracker 上繪製一張由**決策 ticket** 組成的**共用地圖**，並一次解決一張，產出**決策，而不是成品**，直到迷霧被推開、路變得清楚。**`/grill-with-docs`** 磨利的是你能在一個 session 中掌握的想法，wayfinder 則是給你掌握不了的想法，而且它更慢、更密集，所以只把它留給這種情況，絕不用於範圍明確的功能。

  地圖清楚之後，**它負責交接，而不是建置**：在 **`/to-spec`** 匯入主流程，由它把地圖中連結的決策收斂成一份可建置的計畫，然後照常進行 `/to-tickets` 與 `/implement`。把地圖直接接到 `/implement` 會跳過這次收斂，並丟掉連結的細節，所以只有在這項工作最後證明真的很小時，才直接進入 `/implement`。

## 程式碼庫健康

不是功能開發，只是維護。

- **`/improve-codebase-architecture`** 在你有空檔時隨時執行，讓程式碼庫保持在適合 agent 運作的狀態。它會找出**加深的機會**；挑選其中一個就會*產生一個想法*，你可以把它帶進主流程的 `/grill-with-docs`。它是找出候選項目的勘查；**`/codebase-design`**（見下方）則是你設計選定項目的工作台。

## 底層的詞彙

兩個模型觸發的參考資料，在其他 skill 的*底下*運作，各自是它那套詞彙的單一事實來源。當問題出在**用詞**而不是流程時，直接使用它們；或讓上面的 skill 把它們拉進來。

- **`/domain-modeling`**：磨利專案的*領域*語言：質疑一個模糊的術語、解決一個多義詞（「account」同時身兼三職）、把一個難以逆轉的決策記錄成 ADR。它是 `/grill-with-docs` 所驅動的主動紀律，讓 `GLOSSARY.md` 保持為一份乾淨的詞彙表。
- **`/codebase-design`** 是深模組的詞彙（module、interface、depth、seam、adapter、leverage、locality），用來設計模組的*形狀*：在一個乾淨接縫上的小介面後面放大量的行為。`/tdd` 與 `/improve-codebase-architecture` 都使用這套語言。

## 階段邊界

**階段（phase）**是 session 中的一段工作：拷問、實作、QA。在兩個階段之間的**邊界**上你有五個選擇，而在它們之間做選擇是這整張地圖中最模糊的決策：

- **繼續（Continue）**：留在原地。不花任何成本，也不失去任何東西。
- **`/clear`**：清空視窗，當這裡的一切對接下來的事都不重要時。
- **`/handoff`** 寫出一個可攜的 markdown 檔。用途狹窄：只用於**換一個新的 harness**、**換一個新的目錄**、**交給同事**，或在**階段中途**分岔出一個支線任務。它買到的是可攜性。
- **子代理（Subagent）**：把一個範圍緊縮的任務送到它自己的視窗，並取回一份報告。
- **`/compact`** 壓縮這個情境，並以它作為新 session 的起點。這是**預設值**，位於決策樹的最底端，而不是第一個選擇。

閱讀 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md) 取得排序好的決策樹：五個問題、每個分支背後的理由，以及為什麼第一手資料的成本讓**繼續**成為最先要排除的選項。在邊界**上**做決策；在階段中途，就繼續，或把剩下的工作拆給子代理。

## 獨立的 skill

完全不在主流程上。

- **`/grill-me`**：與 `/grill-with-docs` 同樣毫不留情的訪談，但它是**無狀態的**：不在本地保存任何東西，也不建立 `GLOSSARY.md`。當你**不是在工作目錄中工作**時使用（磨利一個計畫、一個設計、一篇文章，任何底下沒有 repo 的東西）。如果你在一個工作目錄中，就改用 `/grill-with-docs`：它執行同樣的訪談並留下書面紀錄，所以它嚴格來說就是較好的那一個。
- **`/grilling`** 是訪談的基本元件本身：回合、前緣、事實是 agent 的工作而決策是你的。`/grill-me` 與 `/grill-with-docs` 是兩個有名稱的入口，而 `/triage`、`/wayfinder` 與 `/improve-codebase-architecture` 都在內部執行它。只有在你想要一場沒有任何包裝的訪談時，才直接使用它。
- **`/prototype`** 是一個小型、用完即丟的程式，用來回答一個設計問題：這個狀態模型感覺對嗎，或這個 UI 應該長什麼樣子。「用完即丟」是對程式碼寫法的限制，而不是承諾要銷毀它：答案會併入真正的程式碼，而原型本身則以**第一手資料**的形式保存在 main 之外的 `prototype/<name>` 分支上，並從實作 issue 指向它。它是主流程步驟 2 中的繞道，但只要一個設計問題很難在紙上解決，隨時都可以使用它。
- **`/research`**：把閱讀的跑腿工作交給一個**背景 agent**：它以**第一手資料**調查一個問題，然後在 repo 中留下一份附引用的 Markdown 檔。在它閱讀的同時你可以繼續工作。它產出的檔案是要帶*進*主流程 `/grill-with-docs` 的素材，因為研究是為思考提供養分，而不是取代思考。
- **`/to-questionnaire`** 適用於卡住你的東西不在你腦中、也不在程式碼庫中，而是在**別人腦中**的時候，它會寫一份問卷讓對方填寫。它是 `/grill-me` 的反向操作：它不是針對主題訪問你，而是針對**寄送**訪問你（要寄給誰、你需要拿回什麼），並讓問題瞄準落差。拿回來的東西是 `/grill-with-docs` 或 `/to-spec` 的素材。
- **`/wizard`** 用於只有**人類**才能採取的步驟：佈建基礎設施、設定憑證或 CI secret、點過一個陌生的第三方後台、執行一次性的遷移或切換。它會產生一個互動式 bash 腳本，打開每個 URL、擷取每個值，並把它寫進 `.env` 與 GitHub secrets，讓這個程序不再是你每次都要重新跟 agent 解釋的東西。它是模型觸發的，所以 agent 一碰到只有你能通過的關卡，就會使用它。如果 agent 自己就能做，它就應該自己做；這是給真的需要人在迴圈中的情況。
- **`/wait-what`** 是一則訊息沒被理解時的修正工具。在對話中途、在任何其他 skill 之中使用它，agent 就會補上你缺少的背景，用淺白的英文、並使用 `GLOSSARY.md` 的詞彙，重新說明它剛才說的話。它是事後補救；`/grill-with-docs` 才是事前的解藥，因為及早約定的共用語言，才是讓術語根本不會出現的方法。
- **`/teach`**：以多次課程學習一個概念，並把目前的目錄當作有狀態的工作區。
- **`/writing-for-agents`** 是撰寫 agent 會讀取之文件的參考：skill、AGENTS.md、被指向的文件。

## 前置條件

**`/setup-matt-pocock-skills`**：在你第一次使用工程流程之前執行，設定其他 skill 所預設的 issue tracker、分類標籤與文件配置。自訂的 issue tracker 也可以運作。
