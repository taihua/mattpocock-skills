# UI 原型（UI Prototype）

在單一路由上產生**幾個截然不同的 UI 變體**，可從一個浮動的底部列切換。使用者在瀏覽器中切換各個變體，挑一個（或從每個裡面各偷一點），然後把其餘的丟掉。

如果問題是關於邏輯或狀態，而不是某個東西長什麼樣子，那就走錯分支了。請使用 [LOGIC.md](LOGIC.md)。

## 何時適合這種形式

- 「這個頁面應該長什麼樣子？」
- 「在決定之前，我想看看這個儀表板有哪幾種選擇。」
- 「為設定畫面試一種不同的版面。」
- 任何使用者原本會花一整天在腦中三個模糊草圖之間做選擇的時候。

## 兩種子形式：強烈偏好子形式 A

當 UI 原型**緊貼著應用程式的其他部分**時，會容易評估得多：真正的 header、真正的側邊欄、真正的資料、真正的資訊密度。一個獨立的用完即丟路由是真空的：每個變體單獨看都還不錯。只要有一個合理的既有頁面可以容納這些變體，就預設使用子形式 A。只有當原型真的沒有鄰近的家時，才使用子形式 B。

### 子形式 A：調整既有頁面（偏好）

路由已經存在。變體**在同一個路由上**渲染，由 `?variant=` URL search param 控制。既有的資料擷取、參數與認證都保留。只有渲染的部分被替換。這是預設；除非有特定理由，否則就選它。

如果原型的對象目前還沒有頁面，但*自然會存在於某個頁面中*（儀表板的新區塊、設定畫面上的新卡片、既有流程中的新步驟），它仍然是子形式 A。把變體掛載在宿主頁面中。

### 子形式 B：新頁面（最後手段）

只有在要做原型的東西確實沒有任何既有頁面可以容納時才使用（例如一個全新的頂層介面，或一個無法合理嵌入任何地方的流程）。

依照專案既有的路由慣例建立一個**用完即丟的路由**。不要發明新的頂層結構。命名時要讓人一看就知道是原型（例如在路徑或檔名中包含 `prototype` 這個字）。同樣使用 `?variant=` 模式。

在決定採用子形式 B 之前，先確認一下：真的沒有既有頁面可以嵌入嗎？一個空的路由會隱藏有內容的頁面所會暴露的設計問題。

在兩種子形式中，浮動底部列都是一樣的。

## 流程

### 1. 說明問題並選定 N

預設 **3 個變體**。超過 5 個就不再是截然不同，而開始變成雜訊，所以上限就是 5。

用一行寫下計畫，放在原型所在位置或檔案頂端的註解中：

> 「設定頁的三個變體，透過 `?variant=` 切換，放在既有的 `/settings` 路由上。」

不論使用者是否在場可以反駁，這樣做都行得通。

### 2. 產生截然不同的變體

草擬每個變體。每一個都要遵守：

- 頁面的目的，以及它能存取的資料。
- 專案的元件庫或樣式系統（TailwindCSS、shadcn、MUI、純 CSS，不論是什麼）。
- 一個清楚的匯出元件名稱，例如 `VariantA`、`VariantB`、`VariantC`。

變體必須**在結構上不同**：不同的版面、不同的資訊層級、不同的主要操作方式，而不只是不同的顏色。三個稍微調整過的卡片格線不是 UI 原型，那是壁紙。如果兩份草稿出來太相似，就加上明確的「不要使用卡片格線」指引重做其中一個。

### 3. 把它們接在一起

在路由上建立單一個切換元件：

```tsx
// 虛擬碼，請依專案的框架調整
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

子形式 A（既有頁面）：把既有的資料擷取全部保留在切換器之上；每個變體只改變被渲染的子樹。

子形式 B（新頁面）：在 `/prototype/<name>` 下的用完即丟路由掛載同一個切換器。

### 4. 建立浮動切換器

一個固定在螢幕底部中央的小列，有三個部分：

- **左箭頭**：切換到上一個變體（循環）。
- **變體標籤**：顯示目前變體的代號，如果變體有匯出名稱，也一併顯示。例如 `B (Sidebar layout)`。
- **右箭頭**：往後切換（循環）。

行為：

- 點擊箭頭會更新 URL search param（使用框架的路由器，例如 Next 的 `router.replace`、React Router 的 `navigate` 等），讓變體可以分享、重新整理後也不會變。
- 鍵盤：`←` 與 `→` 方向鍵也能切換。當 `<input>`、`<textarea>` 或 `[contenteditable]` 處於焦點時，不要攔截方向鍵。
- 視覺上與頁面有明顯區隔（例如高對比的膠囊形狀、淡淡的陰影），讓人一看就知道它不是被評估的設計的一部分。
- 在正式環境的建置中隱藏：以 `process.env.NODE_ENV !== 'production'` 或同等的檢查控制，這樣即使原型不小心被合併，也不會把這個列交到使用者手上。

把切換器放在單一個共用元件中，讓兩種子形式都能重複使用。放在專案中存放共用 UI 的地方。

### 5. 交出去

提供 URL（以及 `?variant=` 的代號）。使用者有空時就會切換瀏覽。有價值的回饋通常是**「我想要 B 的 header 配上 C 的側邊欄」**，那才是他們真正想要的設計。

### 6. 記錄答案並清理

一旦某個變體勝出，記錄答案（哪個變體以及為什麼），然後依照 [SKILL](SKILL.md) 描述的方式保存原型。把勝出者併入真正的程式碼，其餘的移到用完即丟的分支，而不是放進 main：

- **子形式 A**：把勝出者併入既有頁面；從 main 中移除落選的變體與切換器。
- **子形式 B**：把勝出的變體升級為正式路由；從 main 中移除用完即丟的路由與切換器。

整組變體就是第一手資料，所以它們會放到用完即丟的分支上，而不是丟進垃圾桶，因為留在 main 分支中的變體元件與切換器很快就會腐壞，並讓下一位讀者困惑。

## 反模式

- **只有顏色或文案不同的變體。** 那是微調，不是原型。真正的變體在結構上意見不同。
- **變體之間共用太多程式碼。** 共用 `<Header>` 沒問題；共用 `<Layout>` 就失去意義了。每個變體都應該能自由丟掉版面。
- **把變體接到真正的資料變更操作。** 唯讀的原型沒問題。如果某個變體需要變更資料，就把它指向一個 stub：問題是「這應該長什麼樣子」，而不是「後端能不能運作」。
- **直接把原型升級到正式環境。** 變體程式碼是在原型的限制下寫的（沒有測試、極少的錯誤處理）。併入時要好好重寫。
