# 邏輯原型（Logic Prototype）

一個單一、自成一體的 HTML 檔（一個**可分享的 demo**），讓任何人都能透過點按鈕來操作一個狀態模型。當問題是關於**商業邏輯、狀態轉換或資料形狀**時使用：也就是那種寫在紙上看起來很合理，但只有在用真實案例跑過一遍後，才會感覺不對勁的東西。

因為它只是一個檔案、什麼都不用安裝，你可以把它交給非開發人員（設計師、PM、領域專家），讓他們親自感受這個模型。所以它說的是他們的語言，而不是程式碼的語言。

## 何時適合這種形式

- 「我不確定這個狀態機能不能處理先 X 再 Y 的邊界情況。」
- 「這個資料模型真的能表達……的情況嗎？」
- 「我想在寫出 API 之前，先感受一下它應該長什麼樣子。」
- 任何有人想**按按鈕並看著狀態改變**的情況。

如果問題是「這應該長什麼樣子」，那就走錯分支了。請使用 [UI.md](UI.md)。

## 流程

### 1. 說明問題

在寫程式碼之前，寫下你要做原型的是什麼狀態模型、以及什麼問題。一段話，放在 demo 的最上方（放在看得見的介紹中，而不只是註解）。回答錯問題的邏輯原型完全是浪費，所以要把問題明確寫出來，讓之後可以檢查，不論使用者現在就在看，還是之後離開座位後才回來看。

### 2. 把邏輯隔離成可攜的模組

把實際的邏輯（回答問題的那部分）放在單一個 `<script>` 區塊中，寫成一個小而純粹的模組，之後可以直接拿出來放進真正的程式碼庫。周圍的頁面是用完即丟的；這個模組不是。

正確的形狀取決於問題：

- **純 reducer**：`(state, action) => state`。適合 action 是離散事件、狀態是單一值的情況。
- **狀態機**：明確的狀態與轉換。適合「現在哪些 action 是合法的」本身就是問題一部分的情況。
- **一小組作用於單純資料型別的純函式**。適合沒有隱含的「目前狀態」、只有轉換的情況。
- **有清楚方法介面的類別或模組**：當邏輯確實擁有持續的內部狀態時。

選擇最符合所問問題的形狀，*而不是*最容易接到頁面上的形狀。保持純粹：不碰 DOM、不用 `document`、沒有按鈕處理函式伸進它裡面。頁面呼叫它；沒有任何東西反方向流動。這就是讓原型在它自己的生命週期之後仍然有用的原因：一旦問題得到回答，經過驗證的 reducer / 狀態機 / 函式組可以自己被移植到真正的模組中。

### 3. 建立可分享的 HTML 檔

一個檔案，純 HTML/CSS/JS：沒有框架、沒有打包工具、沒有伺服器，一切都內嵌，所以雙擊就能打開，用 email 傳來傳去也不會壞。任何人打開它就能執行。

為非開發人員而寫。每個標籤都使用**領域語言**，而不是程式碼：按鈕和狀態讀起來要像業務本身，而不是 reducer。用淺白的話解釋正在發生什麼。

用清楚的層級由上到下排版：

1. **標題與一行說明**，說明這個 demo 讓你探索什麼（步驟 1 的問題）。
2. **目前狀態**：完整的相關狀態，以易讀的面板呈現（有標籤的欄位，而不是原始 JSON 傾印），每次點擊後重新渲染，讓變化看得見。在有助於非開發人員理解的地方，標出剛才改變了什麼。
3. **自由操作按鈕**：每個 action 一個按鈕，隨時可用，讓任何人都能以任意順序戳戳看這個模型。每次點擊都會派發對應的 action 並重新渲染狀態。
4. **引導式演練**：一組**情境（scenario）**，每個情境一個分頁。每個分頁有一段簡短、淺白的情境描述（它設定了什麼狀況、要注意看什麼），底下是該情境依序**要按的按鈕**。每一步都是真的按鈕：點擊它會執行那個 action，並移到下一步。開始一個演練時會重設到已知的初始狀態，讓情境每次都以相同方式執行。

選擇能展示棘手情況的情境，也就是那些在紙上難以推理的情況：正常路徑（happy path）、一個刁鑽的邊界情況、一次嘗試做某件應該不合法的事。

保持美觀但克制：乾淨的字體、寬鬆的間距、一個強調色。沒有動畫、沒有花招：沒有任何會和狀態及按鈕爭奪注意力的東西。

### 4. 交出去

把檔案傳給他們，或幫他們打開。他們有空時就會點過演練、自由操作；有趣的時刻是他們說「等等，這應該不可能吧」或「咦，我以為 X 會不一樣」的時候；那些就是*想法*中的 bug，而這正是整件事的重點。如果他們想要新的 action 或新的情境，就加上去。原型會演進。

### 5. 記錄答案與原型

原型回答了它的問題之後，記錄答案，然後依照 [SKILL](SKILL.md) 描述的方式保存原型。邏輯原型專屬的對應方式：經過驗證的 reducer / 狀態機 / 函式組移植到真正的模組中（決策被吸收了）；HTML 外殼則跟著放到用完即丟的分支上，作為第一手資料保存原型，而且因為它是一個自成一體的檔案，在那裡隨時都能輕鬆重新執行。

## 反模式

- **不要加測試。** 需要測試的原型就不再是原型了。
- **不要接上真正的資料庫。** 使用記憶體內的狀態，除非問題本身就是關於持久化。
- **不要通用化。** 不要有「如果之後想支援 X 怎麼辦」。原型只回答一個問題。
- **不要把邏輯和頁面混在一起。** 如果純模組引用了 DOM、`document` 或按鈕處理函式，它就無法被移植了。讓頁面只是包在純模組外面的一層薄殼。
- **不要動用框架、打包工具或伺服器。** 一個收件人雙擊就能開的檔案；React 應用或 dev server 會毀掉「可分享」這件事。
- **不要把 HTML 外殼放進正式環境。** 這個頁面是為了被人手動點過而最佳化的。值得保留的是它背後的邏輯模組。
