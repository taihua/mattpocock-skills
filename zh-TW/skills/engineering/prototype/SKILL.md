# 原型（Prototype）

原型是**回答一個問題的、用完即丟的程式碼**。問題決定了它的形狀。

## 選擇分支

根據使用者的提示、周圍的程式碼，或在使用者在場時直接詢問，判斷要回答的是哪一個問題：

- **「這個邏輯 / 狀態模型感覺對嗎？」** → [LOGIC.md](LOGIC.md)。建立一個可分享的單一 HTML 檔（自由操作按鈕加上分頁式的引導演練），把狀態機推過那些在紙上難以推理的情況，而且非開發人員也能操作。
- **「這應該長什麼樣子？」** → [UI.md](UI.md)。在單一路由上產生幾個截然不同的 UI 變體，可透過 URL search param 與一個浮動的底部列切換。

兩個分支產出的東西非常不同，所以選錯會浪費整個原型。如果問題確實有歧義、而使用者聯絡不上，就預設選擇與周圍程式碼較相符的分支（後端模組 → 邏輯；頁面或元件 → UI），並在原型最上方說明這個假設。

## 兩者都適用的規則

1. **從第一天起就是用完即丟，而且清楚標示。** 把原型程式碼放在靠近它實際會被使用的地方（在它所要原型化的模組或頁面旁邊），讓背景一目了然，但命名時要讓隨意瀏覽的讀者也能看出這是原型，不是正式程式碼。對於用完即丟的 UI 路由，遵守專案既有的路由慣例；不要發明新的頂層結構。
2. **執行起來毫不費力。** UI 原型從專案 task runner 的一個指令啟動：`pnpm <name>`、`python <path>`、`bun <path>` 等等。邏輯 demo 是一個使用者雙擊就能開的 HTML 檔。不論哪一種，啟動它都不需要動腦。
3. **預設不做持久化。** 狀態存在記憶體中。持久化是原型*要檢查*的東西，而不是它應該依賴的東西。如果問題明確涉及資料庫，就連到一個暫用的 DB 或本地檔案，並取一個清楚的「PROTOTYPE, wipe me（原型，請清除）」名稱。
4. **跳過打磨。** 不寫測試、除了讓原型*能跑*之外不做錯誤處理、不做抽象化。重點是快速學到東西。
5. **讓狀態浮上檯面。** 每個 action 之後（邏輯）或每次切換變體時（UI），印出或渲染完整的相關狀態，讓使用者看到改變了什麼。
6. **完成後保存下來。** 把任何經過驗證的決策併入真正的程式碼，然後把原型本身保存為**第一手資料（primary source）**：commit 到一個用完即丟、不在 main 上的分支，並在實作的 issue 上留下指向那個分支的情境指標。也要記錄答案（結論以及它解決的問題），寫在 issue 或 commit 中。main 分支只保留經過驗證的決策。
