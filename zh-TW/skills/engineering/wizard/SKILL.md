# 精靈（Wizard）

**精靈（wizard）**是一個 bash 腳本，一步一步引導人類完成一個手動程序，這種程序手動做很煩，每次都要重新跟 AI 解釋也很煩。它會打開每個 URL、確切地說明要點什麼、複製什麼，擷取這些值，寫到它們該去的地方（`.env`、GitHub secrets），在每個階段都做確認，並顯示還剩幾個階段。它可能用來設定第三方服務、執行一次性的遷移，或把專案從一個狀態轉移到另一個狀態。

令人愉悅的使用者體驗已經由 [template.sh](template.sh) 解決了：逐階段的進度、確認關卡、跨平台開啟 URL（包括 WSL）、隱藏輸入的機密、冪等的 `.env` upsert、`gh secret`/`gh variable` 寫入，以及最後的總結。**你的工作只有界定程序的範圍並撰寫它的各個階段。** `STAGES` 標記之上的函式庫在每個精靈中都一模一樣；這種一致性正是重點：絕不要手動編輯它。

精靈預設是短暫的：為一次執行而建立，存到草稿或 `scripts/` 路徑，工作完成後就刪除。只有在使用者想要一條應該留在 repo 中、可重複執行的設定路徑時，才 commit 它。

## 流程

### 1. 界定程序範圍

找出人類必須執行的每一個手動步驟，以及過程中會擷取的每一個值。先讀 repo，不要憑空發問：

- 對於設定：`.env`、`.env.example`、`.env.*`、`README`、`docker-compose*`、框架設定，以及 `.github/workflows/*`（每一個 `secrets.*` / `vars.*` 引用，都是精靈必須產出的值）。
- 對於遷移或轉換：目前的狀態、目標狀態，以及兩者之間不可逆的操作。

接著把排序好的階段清單以及每個階段產出的值給使用者看，並確認：他們可能會新增、刪除或重新排序。

**完成條件：** 每個階段都依序命名，而且對於每一個被擷取的值，你都知道 (a) 人類從哪裡取得它、(b) 它寫到哪裡（`.env`、一個 GitHub secret、兩者，或都不寫；有些階段純粹是動作），以及 (c) 它是機密（隱藏輸入）還是公開的。

### 2. 描繪每個階段的路徑

為每個階段寫下人類要走的精確路徑：打開哪個 URL、在那裡做什麼、值顯示在哪裡、它要填入哪個變數：例如「Dashboard → Developers → API keys → Reveal test key → 複製」。如果你其實不知道目前的 UI 或確切的指令，就直說，並詢問使用者或查閱文件：絕不要編造可能不存在的步驟。

**完成條件：** 每個階段都能追溯到一個陌生人也能照著做的具體指示。

### 3. 撰寫精靈

把 `template.sh` 複製到目標路徑。把範例階段替換成每個步驟一個 `stage`，依相依順序排列。使用函式庫的輔助函式：`stage`、`say`/`step`、`open_url`、`ask`/`ask_secret`、`write_env`、`set_secret`/`set_var`、`pause`/`confirm`。把 `TOTAL_STAGES` 設為你寫的階段數。

維持範本設下的標準：在詢問某個值之前先打開它的 URL、任何機密都使用 `ask_secret`、每一個要保存的值都用 `write_env`、只對 CI 真正需要的值使用 `set_secret`，並在任何不可逆的操作前使用 `confirm`。每個 `stage` 都會清除畫面，只顯示目前的步驟：讓一個階段只處理一件專注的任務，這樣人類需要的任何東西都不會被捲走。不要碰標記之上的函式庫。

### 4. 驗證並交付

- `bash -n <script>`；如果有 `shellcheck` 就執行它。
- `chmod +x <script>`。
- 不要自己從頭到尾執行它：它會打開瀏覽器，並等待人類輸入。改為靜態地追蹤它：步驟 1 中的每個值都有被擷取，並落在步驟 1 所說的地方，而且每個 `set_secret` 的名稱都與 CI 中的某個 `secrets.*` 引用完全相符。
- 告訴使用者如何執行它。如果這是一條可重複的設定路徑，就 commit 它並從 README 連結過去，讓下一個人執行腳本，而不是去問 AI。
