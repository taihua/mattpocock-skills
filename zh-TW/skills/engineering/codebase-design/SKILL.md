# 程式碼庫設計（Codebase Design）

設計**深模組（deep module）**：在一個小介面後面放大量的行為，放在一個乾淨的接縫上，可以透過那個介面進行測試。在任何設計或重構程式碼的地方，都使用這套語言與這些原則。目標是為呼叫者帶來槓桿、為維護者帶來局部性，並為所有人帶來可測試性。

## 詞彙表

精確地使用這些術語：不要用「component」、「service」、「API」或「boundary」來替代。一致的語言就是重點所在。

**Module（模組）**：任何有介面與實作的東西。刻意不限定規模：一個函式、類別、套件，或跨越多層的切片。_避免使用_：unit、component、service。

**Interface（介面）**：呼叫者要正確使用這個模組所必須知道的一切：型別簽章，但也包括不變式、順序限制、錯誤模式、必要的設定，以及效能特性。_避免使用_：API、signature（太狹隘，它們只指型別層級的表面）。

**Implementation（實作）**：模組內部的東西，也就是它的程式碼本體。與 **Adapter** 不同：一個東西可以是有大型實作的小 adapter（一個 Postgres repo），也可以是有小型實作的大 adapter（一個記憶體內的 fake）。當主題是接縫時用「adapter」；其他情況用「implementation」。

**Depth（深度）**：介面上的槓桿。呼叫者（或測試）每學一單位介面所能使用的行為量。當大量的行為位於一個小介面後面時，模組就是**深**的；當介面幾乎和實作一樣複雜時，模組就是**淺**的。

**Seam（接縫）** _（Michael Feathers）_：一個你不必在該處編輯就能改變行為的地方；模組的介面所在的*位置*。接縫要放在哪裡本身就是一個設計決策，與接縫後面放什麼是分開的。_避免使用_：boundary（與 DDD 的 bounded context 混淆）。

**Adapter（轉接器）**：在接縫上滿足某個介面的具體東西。描述的是*角色*（它填入哪個位置），而不是實質（它裡面有什麼）。

**Leverage（槓桿）**：呼叫者從深度中得到的東西。每學一單位介面就能得到更多能力。一份實作在 N 個呼叫處與 M 個測試中回本。

**Locality（局部性）**：維護者從深度中得到的東西。變更、bug、知識與驗證集中在一個地方，而不是分散在各個呼叫者中。修一次，處處都修好。

## 深 vs 淺

**深模組** = 小介面 + 大量實作：

```
┌─────────────────────┐
│   Small Interface   │  ← 方法少、參數簡單
├─────────────────────┤
│                     │
│  Deep Implementation│  ← 隱藏複雜的邏輯
│                     │
└─────────────────────┘
```

**淺模組** = 大介面 + 少量實作（避免）：

```
┌─────────────────────────────────┐
│       Large Interface           │  ← 方法多、參數複雜
├─────────────────────────────────┤
│  Thin Implementation            │  ← 只是單純轉傳
└─────────────────────────────────┘
```

設計介面時，問自己：

- 我能減少方法的數量嗎？
- 我能簡化參數嗎？
- 我能把更多複雜度藏在裡面嗎？

## 原則

- **深度是介面的特性，而不是實作的特性。** 深模組的內部可以由小的、可 mock、可替換的部件組成；只是它們不屬於介面的一部分。模組可以有**內部接縫**（實作私有、給它自己的測試用），以及位於介面上的**外部接縫**。
- **刪除測試。** 想像把這個模組刪掉。如果複雜度消失了，它只是一個轉傳層。如果複雜度在 N 個呼叫者中重新出現，它就有它存在的價值。
- **介面就是測試面。** 呼叫者與測試跨越同一個接縫。如果你想測試*越過*介面的東西，這個模組的形狀大概就不對。
- **一個 adapter 代表假想的接縫。兩個 adapter 才代表真正的接縫。** 除非真的有東西會在接縫的兩側變化，否則不要引入接縫。

## 為可測試性而設計

好的介面讓測試變得自然：

1. **接收依賴，而不是建立依賴。**

   ```typescript
   // 可測試
   function processOrder(order, paymentGateway) {}

   // 難以測試
   function processOrder(order) {
     const gateway = new StripeGateway();
   }
   ```

2. **回傳結果，而不是產生副作用。**

   ```typescript
   // 可測試
   function calculateDiscount(cart): Discount {}

   // 難以測試
   function applyDiscount(cart): void {
     cart.total -= discount;
   }
   ```

3. **小的表面積。** 方法越少 = 需要的測試越少。參數越少 = 測試準備越簡單。

## 關係

- 一個 **Module** 恰好有一個 **Interface**（它呈現給呼叫者與測試的表面）。
- **Depth** 是 **Module** 的特性，以它的 **Interface** 來衡量。
- **Seam** 是 **Module** 的 **Interface** 所在的位置。
- **Adapter** 位於 **Seam** 上，並滿足 **Interface**。
- **Depth** 為呼叫者產生 **Leverage**，為維護者產生 **Locality**。

## 被否決的框架

- **把深度定義為實作行數與介面行數的比例**（Ousterhout）：這會獎勵灌水實作。我們改用「深度即槓桿」。
- **把「Interface」當作 TypeScript 的 `interface` 關鍵字或類別的公開方法**：太狹隘：這裡的介面包括呼叫者必須知道的每一項事實。
- **「Boundary」**：與 DDD 的 bounded context 混淆。請說 **seam** 或 **interface**。
