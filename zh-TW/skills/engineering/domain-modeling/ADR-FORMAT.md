# ADR 格式

ADR（Architecture Decision Record，架構決策紀錄）存放在 `docs/adr/`，採用流水編號：`0001-slug.md`、`0002-slug.md` 等等。

`docs/adr/` 目錄採延遲建立：只有在需要第一份 ADR 時才建立。

## 範本

```md
# {決策的簡短標題}

{1 到 3 句話：背景是什麼、我們決定了什麼，以及為什麼。}
```

就這樣。一份 ADR 可以只有一段話。它的價值在於記錄「*有*做出這個決策」以及「*為什麼*」，而不是把各個段落填滿。

## 選用段落

只有在真正有價值時才加入。大多數 ADR 都不需要。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：當決策會被重新檢視時很有用
- **Considered Options（考慮過的選項）**：只有在被否決的替代方案值得記住時才加
- **Consequences（後果）**：只有在需要特別指出不明顯的下游影響時才加

## 編號

掃描 `docs/adr/` 找出目前最大的編號，然後加一。

## 何時提議寫 ADR

以下三個條件必須全部成立：

1. **難以逆轉**：之後改變主意的成本是有意義的
2. **沒有背景就會令人意外**：未來的讀者看到程式碼會納悶「他們到底為什麼要這樣做？」
3. **是真正取捨的結果**：當時確實有其他選擇，而你基於特定理由選了其中一個

如果一個決策很容易逆轉，就跳過：反正你直接改回來就好。如果它不令人意外，就沒人會納悶為什麼。如果沒有真正的替代方案，除了「我們做了顯而易見的事」之外也沒什麼好記的。

### 什麼樣的決策符合

- **架構的形狀。**「我們使用 monorepo。」「寫入模型採用事件溯源（event-sourced），讀取模型投影到 Postgres。」
- **不同 context 之間的整合模式。**「Ordering 與 Billing 透過領域事件溝通，而不是同步的 HTTP。」
- **帶有綁定（lock-in）的技術選擇。** 資料庫、訊息匯流排、認證服務供應商、部署目標。不是每個函式庫都算：只有那些要花一季才能換掉的才算。
- **邊界與範圍的決策。**「客戶資料由 Customer context 擁有；其他 context 只能用 ID 引用它。」明確說「不」的決策和說「是」的一樣有價值。
- **刻意偏離顯而易見的做法。**「我們用手寫 SQL 而不是 ORM，因為 X。」任何一位理性讀者會預設相反做法的事情。這些紀錄能阻止下一位工程師去「修正」一個其實是刻意為之的東西。
- **程式碼中看不到的限制。**「因為法規遵循要求，我們不能使用 AWS。」「因為合作夥伴的 API 合約，回應時間必須低於 200ms。」
- **否決理由不明顯的替代方案。** 如果你考慮過 GraphQL，卻因為微妙的理由選了 REST，就記錄下來；否則六個月後又會有人提議用 GraphQL。
