這個 skill 根據目前的對話情境與對程式碼庫的理解，產出一份 spec（規格）。*不要*訪問使用者；只要綜整你已經知道的東西。

issue tracker 與分類標籤詞彙應該已經提供給你了。如果沒有，請告訴使用者執行 `/setup-matt-pocock-skills`。

## 流程

1. 如果你還沒有這麼做，先探索 repo 以了解程式碼庫的現況。在整份 spec 中使用專案領域詞彙表的用語，並尊重你所觸及領域中的任何 ADR。

2. 草擬你要在哪些接縫（seam）上測試這個功能。優先使用既有的接縫，而不是新的。盡可能使用最高層的接縫。如果需要新的接縫，在你能做到的最高點提出。整個程式碼庫中的接縫越少越好：理想的數量是一個。

與使用者確認這些接縫符合他的預期。

3. 使用下方範本撰寫 spec，然後發布到專案的 issue tracker。套用 `ready-for-agent` 分類標籤：不需要額外的分類。

<spec-template>

## Problem Statement（問題陳述）

使用者面對的問題，從使用者的角度描述。

## Solution（解決方案）

問題的解決方案，從使用者的角度描述。

## User Stories（使用者故事）

一份很長、有編號的使用者故事清單。每個使用者故事的格式應為：

1. 身為 <角色>，我想要 <功能>，以便 <好處>

<user-story-example>
1. 身為行動銀行的客戶，我想要看到我帳戶的餘額，以便對我的支出做出更明智的決定
</user-story-example>

這份使用者故事清單應該極為詳盡，涵蓋這個功能的所有面向。

## Implementation Decisions（實作決策）

已做出的實作決策清單。可以包括：

- 將要建立或修改的模組
- 這些模組中將被修改的介面
- 開發者提供的技術性釐清
- 架構決策
- Schema 變更
- API 合約
- 特定的互動方式

*不要*包含具體的檔案路徑或程式碼片段。它們可能很快就會過時。

例外：如果某個原型產出了一段程式碼，它比文字更精確地表達了某個決策（狀態機、reducer、schema、型別形狀），就把它內嵌在相關的決策中，並簡短註明它來自原型。只保留富含決策的部分，不是一個可運作的 demo，只要重要的部分。

## Testing Decisions（測試決策）

已做出的測試決策清單。包括：

- 說明什麼是好的測試（只測試外部行為，不測試實作細節）
- 哪些模組會被測試
- 測試的前例（也就是程式碼庫中類似類型的測試）

## Out of Scope（範圍外）

說明哪些東西不在這份 spec 的範圍內。

## Further Notes（其他備註）

關於這個功能的任何其他備註。

</spec-template>
